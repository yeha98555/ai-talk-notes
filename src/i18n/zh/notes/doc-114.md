---
title: Local AI 201：推論引擎與硬體堆疊
speaker: Ahmed Osman 與 Mike，Osmantic（另有 Alex，Exo）
---
這場直播是先前 local AI 入門場次的進階延伸，目的是釐清推論引擎、量化函式庫與硬體選擇這個龐雜生態系。核心論點是：推論引擎從來不只是「硬體加模型」，而是硬體、模型、伺服引擎三者的綜合結果，且三者都不該在確定應用場景之前先行決定。單一使用者的聊天服務與服務二十名並發使用者的代理工作流程是截然不同的問題，因此建議的做法是先確定使用情境，再反推回引擎、模型與硬體，而非反其道而行。

每個推論請求都有兩個階段：prefill（將 tokens 與文件輸入模型的速度）與 decode（生成 tokens 的速度，也就是一般所說的「每秒 tokens 數」）。引擎的真正職責是充當交通警察、記憶體管理員、核心排程器與 API 層，讓多個請求能被妥善處理而不當機。硬體本身的兩個硬性瓶頸是運算能力，以及更關鍵的記憶體頻寬——講者主張頻寬比記憶體容量更重要，因為它決定 decode 速度與實際吞吐量。具體數字：DGX Spark 與 Strix Halo 約在 256–273 GB/s，M5 MacBook Pro 約 600 GB/s，RTX Pro 6000（Blackwell）約 1,800 GB/s。排程器品質與記憶體管理同樣重要，因為它們決定大量請求同時湧入時系統的表現。

在引擎家族方面，llama.cpp 被定位為最友善、最具可攜性的選項——幾乎可在任何裝置（甚至樹莓派）上運行，但未必是任何單一平台的最佳解；vLLM 與 SGLang 則是為並發、多使用者、多 GPU 服務而生，採用 continuous batching 等技術。講者也提供了一頁式決策指南與選擇引擎前該問的九個問題，再次強調答案會因你是要打造單一使用者聊天機器人還是多使用者代理系統而截然不同。

選擇在本地端運行的理由主要有三：成本控制（重度使用者的硬體投資回本期，觀察到最快僅需四到六個月）、隱私與安全（完全掌控自架堆疊，而非信任第三方 API）、以及穩定性（本地調校好的堆疊不會像上游 API 那樣悄悄改變，且理論上可長期不變地運行）。

現場的「硬體競技場」示範，讓 RTX Pro 6000、DGX Spark、Strix Halo 與 M5 MacBook Pro 同時執行相同的 Qwen3.6 27B Q4 模型。單一提示詞的競速結果完全符合單靠記憶體頻寬所能預測的名次。在同一提示詞連發 50 次的高負載測試中，執行 vLLM 的 RTX Pro 6000 大幅領先，因為 continuous batching 讓它只需處理一次提示詞就能產生 50 組輸出，而非重複計算 50 次，加上更高的頻寬，造成差距被進一步放大。更值得注意的是，M5 MacBook Pro 儘管頻寬約為 DGX Spark 與 Strix Halo 的兩倍，在高負載下表現卻與兩者相當，原因是它所使用的 llama.cpp 核心並未針對其 GPU 妥善優化——清楚說明選錯核心足以完全抵銷硬體優勢。

一場盲測「與雲端競速」的示範，讓本地端的 Qwen3.6 27B 模型與雲端前沿模型（暗示為 GPT 系列）回答同一提示詞。觀眾正確猜出左側是本地模型，主要因為其首個 token 生成速度明顯快於雲端模型的 prefill／網路延遲——說明語音代理等對延遲敏感的應用特別適合在本地端運行。

講者接著介紹了他們的免費開源部署堆疊 ODS，它將過去需要數月手動整合的工作（模型下載、引擎選擇、串接 Open WebUI 或 Hermes 等前端、串接程式碼代理、GPU／溫度監控）簡化為一行安裝指令，即可自動配置出完整的本地 AI 伺服器，只留下最後可自訂的 5% 讓使用者調整。

節目後半段轉由 Exo 的 Alex 主講，他回顧 Exo 約兩年前的創立起因，源於 GPU 取得困難以及對 GPU 出口管制、乃至開放權重模型可能遭禁的擔憂——目標是透過叢集運算讓前沿開放模型能在個人硬體上運行，即便早期成果（例如兩台 MacBook 叢集僅有每秒兩個 tokens）更多是概念驗證而非實用方案。隨著模型在保持能力的同時不斷縮小（如 Qwen 約 350 億參數模型為例），關鍵問題已從「本地能不能跑」轉為「跑得有多好」，而現有的評測網站在這方面表現不足：Artificial Analysis 是為雲端／API 模型設計，著重邊際 token 成本；Spark Arena 則只測量本地硬體的原始 tokens/秒，未衡量任務品質。Exo 的解法是全新網站 local.ai（目前為早期測試階段），它針對多步驟的代理任務（而非單次提示詞）為本地硬體建立評測，繪出每台裝置的「智能程度 vs 完成時間」帕雷托前緣（例如在 DGX Spark 上，Gemma 最快但準確率僅 18%，Qwen 準確率達 74%、耗時約 4 分鐘，Step 最準確但耗時超過 14 分鐘）。每個資料點背後約有 700 次代表性代理任務評測結果支撐，測試涵蓋約 100 台不同規格的 Mac 與多款 Nvidia 硬體，並提供可完整重現的設定供使用者複製。
