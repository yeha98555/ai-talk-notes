---
title: 從第一原理談 Loop Engineering
speaker: Kyle Mistele, HumanLayer
---
這場演講開場先批判目前圍繞「Ralph」loop 的炒作——也就是把一個 prompt 丟進 coding agent 的 bash 迴圈裡跑到收斂為止。Jeff Huntley 原始的 Ralph 技巧對單打獨鬥、做用完即丟系統的駭客來說是把利器，但大多數工程師是在團隊中工作,面對關鍵系統、SLA 與法規義務,盲目的迴圈只會產生沒人想 review 的四萬行 PR。演講的目標是展示如何為真實世界——大型、複雜、由團隊擁有的程式碼庫,以及真正的使用者——設計可行的 loop。

核心概念借用自控制理論,也就是恆溫器、Kubernetes autoscaler、infrastructure-as-code 的協調器、Postgres 的 autovacuum、以及 React 虛擬 DOM 背後的原理。控制迴圈包含:量測目前狀態的感測器(sensor)、描述期望狀態的設定點(set point)、把兩者差距轉換成漸進式變更的控制器(controller),以及套用變更的致動器(actuator)——同時系統會持續受到外部擾動並被重新量測。只要有可量測的東西、改變它的方法、以及取得結果回饋的方式,控制迴圈就非常適用,其運作方式是做出微小、可逆的變更,而非直接衝向終態、冒著系統失穩的風險。這正是「盲目的 Ralph loop」的對立面;而做得好的 Ralph 式迴圈,其實已經在逼近控制理論了。

打造一個 agentic 控制迴圈,首先要定義設定點(程式碼庫希望達到的特性)與感測器,感測器可以是完全確定性的(linter、ASTGrep、型別檢查)、完全 agentic 的(模型加上 skill 與自然語言規則),或是兩者混合的 pipeline。由於 agent 會模糊各元件之間的界線,同一個工具可以同時身兼感測器與控制器(例如一個 React lint agent 既標出問題也排出修復優先序),單一 agent 也能同時扮演控制器與致動器,在同一個 context window 裡做出決策並套用變更。控制器是關鍵所在:如果沒有調校好,迴圈可能一次做出過大或錯誤的變更,一旦放進迴圈裡跑,問題會迅速惡化。

演講以 HumanLayer 內部把 RPC API 遷移到 Effect 函式庫的迴圈為例說明這套模式。感測器使用 ASTGrep——語言無關、獨立於 linter 設定之外(agent 有時會偷偷用行內註解關掉 linter 規則)——在多語言的 monorepo 中找出尚未遷移的 procedure。由於一次完整掃描會產出太多違規項目、無法即時處理,團隊先在 main 分支上跑一次確定性的基準掃描,把排序後的違規清單提交進版本控制,接著設下關卡,不讓新 PR 再新增未遷移的程式碼——這是一種「擾動緩衝器(disturbance dampener)」,先止血,之後再逐步修正。控制器可以簡單到確定性地挑選最小的違規項(以降低風險),也可以更聰明:交叉比對遙測數據,優先處理錯誤最多或監測最弱的 procedure,讓遷移過程順帶改善錯誤處理與可觀測性,而不只是機械式的重寫。致動器是 agent 加上精心設計、持續迭代的 skill,理想情況下會先由人工寫好「黃金範式(golden pattern)」範例,讓 agent 有道地的模板可以依循,而非依賴網路上的泛用知識;它產出的最終回應會被原封不動當作 PR 描述,之後迴圈以確定性方式 commit、push 並開啟 PR。

把這套流程排程成 GitHub Actions workflow(選用它是因為已有存取程式碼、密鑰與排程原語的能力),就能變成每天穩定產出小型、低風險 PR 的節奏。有兩項改良讓它能長久運作:一是把回饋內容寫成受版控管理的 markdown 檔案,每次執行都會載入致動器的 context,並可透過在 PR 留言 `/iterate` 來觸發 workflow 拉取 diff、review 留言與描述,同時修改程式碼與回饋檔案——讓人類能以低摩擦的方式即時導正迴圈方向,且變更歷史可追溯;二是流量控制,每個迴圈執行前都會檢查自己先前標記的 PR 是否仍未關閉,若是則跳過本次執行,確保每個迴圈最多只有一個未經 review 的 PR 存在,避免工作堆積、重複或衝突而無人察覺。當信心提升後,可以讓控制器一次挑選並執行多個違規項、拆成各自獨立的實作階段以取得更便宜、更可靠的 per-item context window,或是把 workflow 分派給整個團隊平行處理。

結語強調,這仍然是在打造 loop——但是以控制理論的紀律去設計的 loop:漸進、可量測、可供人類 review、能自我節流、也能被引導,目的是讓複雜、高風險程式碼庫中的困難問題變得可控,而不是把大量無法閱讀的 agent 生成程式碼一股腦丟給團隊。
