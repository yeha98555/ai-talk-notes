---
title: 唯有日誌:用 AI 代理人重新思考可觀測性
speaker: 創辦人, Sazabi
---
Sazabi 是一個 AI 原生的可觀測性平台，其核心主張是：現代軟體生命週期中最緩慢、最痛苦的一環——在正式環境中找出並修復問題——尚未像撰寫程式碼那樣被顛覆。創辦人曾在 Brex 帶領可觀測性團隊，與 Datadog 這類工具有著愛恨交織的關係，他將 Sazabi 的做法定位為「為可觀測性打造 AI，而非為 AI 打造可觀測性」，並提出三項與傳統可觀測性作法大相逕庭的宣言。

第一項主張是使用者永遠不該直接查看原始遙測資料——沒有儀表板、火焰圖或服務地圖。取而代之的是，可觀測性最好的使用者體驗就是聊天：一個能存取你日誌、程式碼庫與其他脈絡的代理人，直接回答問題（系統是否正常、為何某客戶受影響、哪個 commit 導致故障），如同開發者如今已不再親自閱讀自己的程式碼一樣。第二項更具爭議的主張，是揚棄傳統的「三大支柱」——指標、日誌、追蹤——只保留日誌。指標與追蹤是儀器化中最困難的部分（設定 Prometheus、傳遞 span context、區分 counter 與 gauge），因此 Sazabi 完全捨棄它們，只要求類似 console log 的輸出，再由後端重建出指標與類似追蹤的結構。第三項主張宣告靜態監控與門檻值已死：與其用 AI 去篩選或豐富既有告警，Sazabi 直接用 AI 生成告警本身——基於代理人對日誌、程式碼與脈絡的判斷，非確定性地決定何時值得通知——同時 Sazabi 明確拒絕自己撰寫或合併程式碼，堅持唯讀，而是將修復工作交給 Cursor 或 Claude Code 之類的工具，或依使用者設定並由記憶保存的偏好，在 Linear 等系統中建立工單。

關於工具暴露的討論，比較了 MCP 與基於 CLI/沙箱的工具使用方式，以及 Skills。MCP 的脈絡膨脹問題來自於一開始就載入大量工具定義，業界已透過工具搜尋與漸進式揭露來緩解。以 CLI 驅動的代理人在沙箱中則能避開此問題，因為標準 Unix 工具實際上已內建於模型權重中——代理人本就「知道」cat 或 grep 可能存在，直接嘗試即可。Skills 同樣避開了膨脹問題：代理人只讀取簡短的 markdown 標頭作為目錄，按需載入完整細節，不過與談者也指出，過度熱衷建立 skill 可能重蹈 MCP 膨脹的覆轍。

在架構上，Sazabi 的代理人建構於 Vercel AI SDK workflows 之上，以 Daytona 沙箱與一個 bash 工具作為主要介面，另外配有一個專用的唯讀、類 SQL 查詢工具，透過代理伺服器並搭配資料列層級安全性存取日誌資料庫。原始碼則透過將目標儲存庫複製進沙箱檔案系統來取得，使代理人能將日誌中的錯誤與特定 commit、檔案、行號建立關聯。記憶完全建立在檔案系統與 git 之上，類似 OpenClaw 的 markdown 檔案作法：每個「專案」（例如 staging 或 production）各自擁有一個 git 儲存庫，每個對話串則對應一個分支，在沙箱啟動時拉取、每次指令結束後推回，藉此在不使用傳統資料庫的情況下實現跨沙箱的持久化、可共享狀態。多個對話串或子代理人可同時寫入共享記憶，衝突則交由背景工作流程以 git merge conflict 的方式解決——這模擬了傳統交易型資料庫的保證，卻是以檔案操作的形式呈現，創辦人認為這比 Postgres 介面更貼近代理人的天性。主代理人平行派生的子代理人各自擁有獨立沙箱，卻共享這套以 git 為底層的記憶，因此後派生的子代理人能受益於先前代理人的發現（視派生時序而定）。這也呼應了源自 GEPA 等演化式提示優化方法的更廣泛構想：對同一任務平行執行大量代理人，再挑選或合併最佳輸出——這是一種「map」，而目前的工具（包括 Codex 的背景代理功能）仍普遍缺乏良好的「reduce」步驟。

評測被視為必要但次要的環節，良好的脈絡工程、沙箱設計與子代理人架構本身就能帶來大部分的品質提升；評測的作用在於把專屬的日誌資料轉化為回饋訊號，將代理人推向頂尖水準。相較於結構化的工具呼叫，針對以 CLI/bash 為主的工具使用進行評測明顯困難得多，因為沒有單一、離散的動作可供檢查——一個「執行指令」的 bash 工具可能透過 curl、腳本或多種不同的參數組合來觸發告警，這迫使團隊要嘛用 LLM 對指令字串做模糊比對，要嘛去檢查相依服務端的實際副作用（例如 API 端點是否真的被呼叫）。但隨著沙箱允許使用者安裝任意工具、產品野心持續擴大（例如在 AWS 上自動擴展 Kubernetes 叢集），評測環境勢必要模擬越來越大範圍的真實世界，讓「讓產品更強大」與「保持可測試性」之間的張力日益加劇——目前的務實做法是盡量以本地替代品（本地 Postgres、LocalStack）取代真正的外部相依服務，並在採用 Turborepo 的 TypeScript monorepo 中自行打造評測工具，而非購買現成的評測平台。

最後談到安全與合規：Sazabi 預設嚴格唯讀，且無法存取公開網路，只能連到白名單內的網域／IP，這正是為了防止提示注入導致程式碼或日誌外洩。團隊也會評測代理人是否洩漏自身實作細節，以此作為競爭優勢的保護措施，同時具備創辦團隊過往打造銀行基礎設施經驗所帶來的一系列企業級認證（SOC 2 Type II、ISO 27001、GDPR、HIPAA）。
