---
title: 為什麼我們自建 Feature Store(以及它如何讓 Rokt 的 ML 得以擴展)
speaker: Aanashani, Rokt
---
Rokt 的業務是在電商的「交易時刻」——選擇頁、購物車頁、付款頁、確認頁——做即時個人化,即時為數千種優惠組合評分,並在 250 毫秒內回傳最佳排序結果,每年支撐數十億筆交易。其 ML 技術堆疊從簡單的規則式批次邏輯,演進到具備即時評分的邏輯迴歸,再到梯度提升樹,最後走向深度學習,每一步基礎設施都跟不上,並暴露出新問題:特徵邏輯零散、訓練與線上服務不一致,以及特徵、嵌入向量、輸入資料量增加所帶來的壓力。

在沒有 feature store 之前,情況相當混亂。同一套特徵轉換邏輯被重複撰寫——訓練用 SQL、線上服務用 Go——造成不一致且難以追蹤的錯誤。訓練與線上服務不一致(training-serving skew)是最棘手的問題:模型離線表現亮眼,一上線卻失靈,因為兩邊的特徵計算方式不同。系統也缺乏「時間點正確性」(point-in-time correctness),導致模型可能洩漏未來資料,看似準確卻無法泛化;特徵散落在筆記本、訓練程式碼與各服務中,沒有明確歸屬。這些缺陷代價高昂:一個延宕已久的錯誤修復後,發現原本可能帶來 500 萬到 700 萬美元的營收提升;另一個訓練錯誤則單獨造成 17 萬美元的損失。

解方需要五件事:每個特徵都有共享的定義、將時間點正確性內建於系統而非依賴個人自律、訓練與服務邏輯一致、自助式導入讓資料科學家與 ML 工程師能獨立迭代,以及每個特徵都有明確的歸屬與血緣。這正是 feature store 所承諾的——一次定義、具版本控制、時間點正確,並可在訓練與即時推論間重複使用的單一事實來源。

Rokt 曾在 2020 至 2021 年間評估採用現成的 feature store,但遇到幾個特定於其業務的障礙。由於 Rokt 沒有穩定的使用者 ID(使用者不像在 Facebook 或 Google 那樣登入),其身分系統需串接多個 session key,而多數 feature store 當時只支援單一鍵值查詢。Rokt 還需要在 60 毫秒內完成的即時(on-demand)轉換、對陣列與時間戳記的支援,以及與既有技術堆疊的緊密整合——當時的現成工具若不大幅妥協,無法滿足這些需求。因此團隊決定自建,以求更快的速度、更深的整合,以及對自身路線圖的掌控權。

最終系統涵蓋三大核心流程。在實驗階段,一套領域特定語言(DSL)用來定義特徵,並登記到本地命名空間下的 feature registry 中,讓資料科學家能在不影響正式環境的情況下測試新特徵,由 SDK 依需求計算數值。在正式化階段,將特徵推向正式環境會觸發 materializer,執行 Spark on Kubernetes 任務(為提升可擴展性已從 EMR 遷移而來),把特徵資料從資料湖或 Kafka 推送到線上儲存——Rokt 已將此儲存從 DynamoDB 遷移到自建的 Cassandra 叢集,以在特徵量成長時控制成本。在即時服務階段,線上 API 使用預取 DAG(prefetch DAG)計算相依特徵、避免重複運算,Go SDK 決定要查 Cassandra 還是使用請求中的上下文,而 UDF 執行器(為提升並行效能已從 Python 遷移到 Go)負責執行最終轉換,整體落在 60 毫秒 P99 延遲預算內。

這帶來了貫穿整個 ML 生命週期的成效:特徵可重複使用,不再是各模型各自撰寫 SQL 與 Go;統一邏輯消除了訓練與服務間的漂移;自助式 AB 測試不再仰賴平台工程師;透過時間點快照與版本控制實現可重現性;以及集中式登記機制取代分散式定義,並附帶血緣與歸屬資訊。

歷經三年建置與演進之後,結論是:對於想加速 ML 創新的組織來說,feature store 確實是遊戲規則的改變者,但自建或採購的決策取決於契合度——現成工具如今已能涵蓋約八成的使用情境且持續快速演進,多數團隊應優先採購;但若有特殊需求(如 Rokt 缺乏穩定使用者 ID),則可能需要自建。無論哪種選擇,feature store 都應被視為長期的核心基礎設施,而非附屬專案,因為它將成為讓 ML 從實驗到服務端到端保持一致且可擴展的骨幹。
