---
title: 框架工程還不夠：軟體工廠為何失敗
speaker: Dex Horthy, HumanLayer
---
這場演講從 AI coding 領域的主流敘事說起：模型已經夠好了、程式碼是免費的、你才是瓶頸，所以應該多花 token、不必再讀程式碼。但講者指出裂痕正在浮現——原本不該因為 coding agent 出包而當機的公司開始當機，程式碼庫比以往更快劣化，而 Faros AI 的報告顯示，自從團隊普遍採用 AI coding 工具以來，pull request 審查品質下滑、留言變多變長、許多 PR 完全未經審查就合併，事故與每位開發者的 bug 數都在上升。核心論點是：這不是靠更多框架工程或更聰明的迴圈就能解決的規模問題,而是模型訓練層面的問題。

為了說明這點，講者回顧「軟體工廠」的簡史（這個詞源自 1968 年北約會議）。在 2022 年的軟體工廠中，工程師從追蹤系統領取工作、開發、通過 PR 審查與測試後上線,使用者回饋與監控再回流到規劃階段。團隊早就明白，事前的規劃與架構討論能減少返工、縮短審查週期。agentic 軟體工廠只是把「建置」這一步換成 agent，時間從數天縮短到數分鐘——但人力審查與測試仍是瓶頸。自然而然的下一步是導入 agentic 程式碼審查與回歸測試，接著把事故與使用者回饋直接餵回 agent 迴圈，最終走向 Dan Shapiro 所說的「熄燈軟體工廠」：完全放棄程式碼審查,唯一要做的決定只剩下要塞多少工作進佇列。講者明確表示這行不通,並以 HumanLayer 自身在 2025 年 7 月全面「熄燈」的經驗為證：幾個月後便遇到即使用最進階的提示也解決不了的問題,必須回頭深入已經數月沒人讀過的程式碼,同時網站當機、使用者憤怒。

根本問題在於：若沒有相當程度的人工引導,模型無法長期維持並提升程式碼庫品質——程式碼庫會變得脆弱,改一處就牽連他處崩壞(Martin Fowler 所謂的「霰彈式手術」壞味道)。即使是最新的模型也是如此:它們在一次性任務與全新專案上進步很多,但在長期可維護性上並無明顯進步,部分原因是目前根本沒有衡量這項能力的好基準測試。

講者接著解釋原因:儘管 Aider、Codebuff 等其他 CLI agent 擁有和 Claude Code 相同的 read/write/edit/grep/bash 工具集,為何 Claude Code 卻成為第一個突破性的 coding agent?關鍵在於 Anthropic 是第一個直接針對自家要發布給使用者的框架來訓練模型的實驗室,讓模型能針對自己的工具呼叫迴圈做 RL——這是沒有模型權重的框架開發者難以匹敵的優勢。以類似 SWE-bench 的任務為例,標準的 coding RL 會產生大量解題軌跡,依「測試是否通過且未破壞其他部分」評分,再強化成功的軌跡。但這種獎勵訊號只檢驗測試是否通過,完全不檢查程式設計品質,因此像是為了讓測試過關而硬加不必要的 try/catch、或做型別強制轉換這類醜陋補丁都不會被懲罰——因為驗證可維護性遠比驗證測試通過困難得多,劣質架構的代價往往要數月甚至數年後才顯現,幾乎不可能把這個獎勵訊號回傳到訓練當下的那一集(episode)。

較新的基準測試正試圖填補這個落差——Abundant AI 的 SWE Marathon 設計了約 400 小時、重建整個 Excel 功能等級的任務;DataCurve 的 Deep Suite 使用大型、未曾出現在訓練集中的真實專案;Cognition 的 Frontier Code 則會懲罰那些在補丁前程式碼上不會失敗的測試,並用評判模型檢查程式碼品質規則。但講者認為評判模型的效果終究有其天花板:如果模型真的懂得什麼是好程式碼,它一開始就會直接寫出好程式碼;審查型 agent 與砸更多 token 只能提高下限,無法突破目前 RL 能教會模型的範圍。因此結論是:現階段我們仍然得親自讀程式碼。

基於此,實務建議是圍繞這項限制重新設計工作流程,而非坐等更好的模型。具體做法是重新打開程式碼審查,並在事前投入產品審查(釐清問題與期望行為、搭配設計稿)、系統架構(元件契約、資料模型、限制條件),以及常被忽略的「程式設計」階段(型別、方法簽章、程式版面配置與呼叫堆疊/呼叫圖,Cloudflare 的 Dylan Mulroy 也採用類似做法),接著是「垂直切片」——定義整個系統的實作順序與檢查點。事前花 30 分鐘規劃與對齊,能在審查階段省下數小時,使得逐行閱讀程式碼仍屬可行。PR 淹沒團隊的真正原因不是 PR 太多,而是「爛」PR 太多;一份對齊良好的 PR 讀起來令人愉快,而即使只需要 20% 返工的 PR,對提交者與審查者雙方都是沉重的情緒與智力負擔。借助模型輔助規劃,對齊更快(因為一次性取得所有資訊)、審查更快(因為事前已對齊)、編碼更快(因為 AI 完成),團隊因此能真正加速,同時仍然擁有並閱讀自己的程式碼。

演講最後將整個問題重新定義為「在限制條件下做工程」,而非悲觀的理由:模型有其擅長與不擅長之處,任務是在這些限制內找到槓桿點,而非假設模型終將變得夠好。講者所屬的 HumanLayer 正在打造一個 AI IDE 與協作平台——類似 Figma 式的協作工作空間,用於支援 Claude Code / Codex 風格的工作流程,以貫徹「先規劃後審查」的方法,並將更完善的軟體品質驗證器列為未來方向。
