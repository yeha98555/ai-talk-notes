---
title: 為什麼 AI 代理需要的是「資料挽具」，而不只是 Lakehouse
speaker: Will Martin, Dremio
---
這場演講一開頭就提出一個框架轉換：傳統分析走的是「email 節奏」——一次查詢花上幾分鐘或幾小時都算正常，因為人可以先去泡杯茶再回來看結果。但代理式（agentic）工作流走的是「對話節奏」——如果代理必須等十秒才拿到資料，整個管線就會卡住、token 被浪費，互動也就中斷了。次秒級的回應對 AI 驅動的資料存取而言不是錦上添花，而是硬性要求，而這正是區分「單純的 data lakehouse」與講者所謂「資料挽具（data harness）」的關鍵。

背景鋪陳是相當標準的 lakehouse 敘事：資料倉儲（warehouse）擅長查詢但儲存成本高昂；資料湖（lake）儲存便宜但查詢困難；lakehouse 則結合物件儲存的低成本與 metadata catalog、table format（Iceberg）帶來的類倉儲級可靠交易，兼取兩者之長。Dremio 自家技術棧完全建立在開放標準之上——Parquet 作為檔案格式、Iceberg 作為唯一的 table format、Apache Polaris 作為開放 catalog，以及以 Arrow 為基礎的查詢引擎——演講主張，這種對開放標準的堅持（相對於封閉、廠商專屬的技術棧）本身就是打造一套不被綁定的挽具的前提條件。

執行層的三個元件被視為共同構成「效能資料挽具」：catalog、語意層（semantic layer）與查詢引擎。Catalog（Polaris）負責治理與最佳化——角色型與細粒度的列/欄存取控制、一路下探到儲存層級的憑證授予（credential vending），以及表格維護機制，如解決「小檔案問題」的壓縮合併（compaction）、清除過時 metadata 的 vacuuming，以及作為分區（partitioning）更友善替代方案的 Iceberg clustering。一項較新的特性——variant shredding——讓半結構化（類 JSON）資料可以放進表格的一個欄位，同時仍能被拆解出來以支援 predicate pushdown，藉此保留讓 table format 得以高速運作的查詢裁剪能力。

語意層處理的是一個早於 AI 就存在、卻因 AI 而被放大的問題：像「客戶」或「營收」這類商業術語，即使在同一家公司內部也很少有統一定義，而這些定義往往存在於資料平台之外——BI 工具、試算表，或人們的腦海裡——人與模型都難以觸及。以一般資料訓練出的 LLM 並不掌握某家公司的特定定義，只會「自信地亂猜」，產出的結果沒人能真正信任。把指標定義、表格關聯與欄位意義整合進與資料放在一起的單一語意層，能讓代理在寫查詢之前，有一個可靠的地方去解析模糊的商業語言。演講也提到業界正在興起的相關努力——Open Semantic Interchange（OSI），如今已成為 Apache 軟體基金會旗下、由 Salesforce、Snowflake 等公司支持的專案，目標是標準化語意脈絡在不同工具間的共享方式，儘管具體實作目前仍各有差異。

查詢引擎的角色是資料聯邦（federation）：不是把資料實體集中起來（這正是資料倉儲當初落入的陷阱），而是在資料所在之處直接查詢——橫跨孤立系統、其他 catalog、資料庫與物件儲存，把存取與治理集中化，但不把儲存集中化。效能則來自多層快取——查詢計畫快取（query plan caching）、結果集快取，以及一種將常用資料保留在運算節點上的欄式雲端快取（columnar cloud cache），透過善用原本閒置的本地儲存空間，據稱可為部分客戶節省高達 90% 的成本。

由於這一切都建立在開放規格之上——尤其是 Iceberg REST 規格——引擎與 catalog 在很大程度上可以互換：任何相容的引擎都能開箱即用地與任何相容的 catalog 溝通，讓團隊得以依照自身的效能、成本或組織限制來組建 lakehouse 平台，而不是被綁死在單一廠商身上。AI 進入此挽具的方式有三種——供非技術使用者使用的內建 UI 代理、用於一般整合的 MCP，以及用於程式化、多代理工作流的 CLI——語意層則作為這三種方式底層共通的脈絡與權限邊界，確保代理永遠是以其所代表的、已獲授權的使用者身分在查詢。

結尾總結出分析與工程工作負載共同的需求：資料必須是可存取的（受治理但廣泛可達）、可理解的（透過共享、經一致同意的語意定義，而非臨場各自解讀）、以及高效能的（就地查詢，不做不必要的搬移或等待）——而這一切都應該建立在開放標準之上，讓組織不必被綁定在單一廠商身上才能實現。
