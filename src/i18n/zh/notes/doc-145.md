---
title: 效能優化的 AI 代理:更快上線、更省成本
speaker: Rajat Shah, Netflix
---
這場演講提出了一套實務手冊,說明如何運用 AI 代理來彌補「AI 加速編碼」所帶來的落差:工程師現在能以遠超以往的速度產出程式碼,但這些程式碼不見得具備高效能;而人類效能工程師找出並修復瓶頸的傳統流程——觸發效能分析、下載原始呼叫堆疊資料、載入視覺化工具、逐一尋找熱點路徑、搜尋程式碼庫、最後送出修復——每個服務都要耗費大量繁瑣且專業的工時,因此除非遇到凌晨兩點的救火事件,否則很少真正執行。

核心問題是:LLM 代理能否取代這 20 分鐘的人工排查流程?這個想法之所以可行,基於兩個前提:效能分析輸出的結構在不同語言與執行環境間高度相似(呼叫堆疊、自身 CPU、累計 CPU,並以高頻率取樣),因此代理不需要語言專屬工具即可解讀;而編碼代理已從公開程式碼中見過足夠多常見反模式——O(N²) 迴圈、迴圈不變量重複運算、重複的物件配置、錯失的批次處理機會——僅憑呼叫堆疊的形狀即可辨識,甚至不必檢視原始碼。實務上,一旦代理在效能分析資料中發現可疑模式,便能檢出對應的正式環境版本、定位方法、追蹤完整呼叫路徑並提出修復方案——這四個步驟在大型程式碼庫中可於五分鐘內完成。其中一個真實案例揪出一個佔用 8.8% CPU 時間的 O(N²) 實作;另一案例中,代理將單一反模式(每次熱點路徑迭代都重新建立的指標計數器物件)加以類推,跨儲存庫搜尋後發現同一反模式在七個不同服務中重複出現,若全部修復,估計可節省 0.5% 至 4.6% 的 CPU 用量。

為了讓這套做法系統化而非一次性,關鍵基礎建設是建立一套長期、跨服務共用的模式與反模式記憶庫——不需要向量資料庫,只需在中央 Git 儲存庫中維護 markdown 檔案,供人類與代理共同讀寫。每筆條目記錄相關符號、已確認出現該模式的服務,以及隨更多服務驗證而提升的信心分數。這個目錄可從公開資源(例如 Jeff Dean 的 C++ 優化筆記、PyTorch 的 torchfix 反模式庫)或組織自身的效能手冊起步,並會隨時間複利成長:一旦某服務的效能分析找出某個模式,日後任何服務的代理都能立即重複利用該發現,無需從頭再來一次。

由於代理修改已在正式環境穩定運行的程式碼本質上具有風險,人類核准仍須保留在流程中,而在送交人類審查前需先過濾雜訊:代理必須先通過既有的單元測試與整合測試,接著執行金絲雀測試,在正式流量下比較新舊程式碼的 CPU、延遲與錯誤率差異。唯有同時通過功能正確性檢查與金絲雀真實驗證的修復方案,才會被提交為程式碼審查——其心智模型是:效能分析器提供估計值,金絲雀測試提供真實依據,而最終決策仍由工程師做出。

長期目標是將這套流程沿著軟體開發生命週期往「左」推移:從被動模式(找出並修復已存在於正式環境中的不良模式),進展到審查階段由審查代理依據目錄以行內註解標示反模式,理想情況下更能在撰寫程式碼的當下就攔截問題——編碼代理在產生程式碼前先查閱目錄,讓低效程式碼從一開始就不會被寫出。這種在撰寫階段的整合會增加延遲與 token 成本,因此目錄必須妥善索引,支援階層式、低情境負擔的查詢,而非一股腦塞進提示詞中。

總結建議強調:在疊加代理自主性之前,務必先打好基礎——扎實的測試覆蓋率、可靠的金絲雀自動化,以及維護良好的模式目錄;並建議從被動路徑起步,而非一開始就試圖自動化一切。演講將此框架為自主性的分階段光譜:第一階段是完全人工的效能分析,沒有 LLM 參與;第二階段——也是本次演講的重點——是固定、預先定義的代理工作流程(觸發效能分析、分析、執行金絲雀測試、提出修復方案),可排程每週執行以攔截新出現的退化;第三階段則賦予代理開放式的規劃與推理自主權,但需大量投入評估與沙箱機制,以防範提示注入等安全風險。建議做法是從第一階段起步,推進到第二階段以獲取多數效益,唯有在防護措施到位後才考慮邁向第三階段。
