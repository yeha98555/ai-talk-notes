---
title: 訓練 Agent 系列 3:強化學習
speaker: Ben 與 Sergio Paniego, Hugging Face
---
這是 Hugging Face 訓練 agent 直播系列的第三場,前兩場分別談 SFT-on-traces 與蒸餾(distillation),而第四場將把同一套演算法套用到真正的 RL 環境中。三者共通的主軸是學習訊號的密度:SFT 提供密集的逐 token 目標可供模仿,但受限於訓練資料本身的「模仿天花板」;on-policy 蒸餾則針對模型自己生成的軌跡,由教師模型給出密集的逐 token 回饋,資訊更豐富,但仍受限於教師的知識邊界;強化學習則只提供一個稀疏訊號——軌跡結束時的一個 reward——但這個訊號是貨真價實的 on-policy,讓模型能從自己的嘗試中學習,而非模仿他人。實務上的訓練管線通常會串接這些方法:先用 SFT 把模型拉到堪用的基準(如同閱讀大師棋譜),再用 RL 透過自身的試錯進一步提升(如同真正下場比賽)。

本場聚焦的演算法是 GRPO(group relative policy optimization)。一個 GRPO 步驟會取一個 prompt,從目前的策略中取樣出一組(而非單一)完成結果,用 reward function(通常就是一段 Python 程式,例如檢查棋步是否合法、任務是否成功、或單元測試是否通過)為每個結果評分,再把原始 reward 轉換成每個結果的 advantage:該 reward 減去該組平均值,再除以該組標準差。真正驅動策略更新的是這個「組內相對」的 advantage,而非絕對 reward,這也是為何一組內的組成與變異程度如此關鍵——若一組內所有結果全部成功或全部失敗,就完全沒有相對訊號可學。訓練過程中有兩道護欄防止策略偏離太遠:KL 散度懲罰(參數 beta)讓策略偏離初始行為的代價變高;以及裁剪(clipping,參數 epsilon)限制單一批次的更新幅度。這兩者在 TRL 中預設為零,需要刻意調整。

Reward function 被形容為定義「成功」究竟是什麼的一份契約,也是 RL 中真正需要下苦功的地方——多數專案的迭代精力其實都花在把 reward function 設計對,而非訓練迴圈本身。常見做法是把「格式」reward(輸出結構是否正確,例如是否為合法棋步或標籤是否完整)與「準確度」reward(底層答案或任務是否真的正確)疊加起來,因為模型可能格式正確但答案錯誤,或答案正確但格式有誤,這些組合理應得到不同分數。這種 reward shaping(即便準確度訊號還學不到之前,先給格式訊號部分獎勵)有助於製造一組內所需的變異,也是避免任務「太難」(沒有訊號,如同業餘者每場都對上大師)或「太簡單」(同樣沒有訊號,如同大師每場都碾壓業餘者)的關鍵。DeepSeek 論文中提到的「aha moment」,指的正是變異累積到足夠程度、學習明顯開始起飛的那個時刻。

Reward hacking——模型找到某種捷徑,拉高 reward 卻沒有真正解決任務——幾乎是不可避免的,只要 reward function 存在任何可鑽的漏洞(例如過於寬鬆的正規表示式,或定義含糊的勝利條件)。KL 懲罰能讓 hacking 稍微付出更高代價,因為 hack 出來的行為通常遠離模型初始(SFT 後)的分布,但這並非真正的解方,因為它同時也會抑制其他有用的新行為。真正的防線是持續觀察指標(熵值下降但 reward 卻持續上升就是警訊),並不斷檢視底層軌跡與資料本身,而非只盯著 reward 曲線;另外保留一組獨立的 test reward 訊號、使其應與 training reward 同步變化,train 與 test reward 之間拉開差距,正是最明顯的破綻。

本場也把 GRPO 拿來與 DPO 對照:DPO 是離線方法,在固定的「被選中/被拒絕」配對資料上訓練,並與凍結的參考模型比較——設定較簡單,但若資料已過時,能提供的訊號可能不比策略本身已知的更多;online DPO 則介於兩者之間。PPO 則是最早期 InstructGPT 式 RLHF 背後的演算法,更為複雜,需要額外訓練一個 reward model 為每次生成評分,增加了成本,但能捕捉風格類等難以用確定性函式表達的特質;儘管如今很少作為首選,其許多概念仍延續到後續各種 LLM 用 RL 方法中。

對應到 TRL 的 GRPOConfig,整個迴圈的可調參數包括:取樣階段的 temperature 與 num_generations(組大小)、最大完成長度、是否使用 vLLM 做推論;多個 reward function 之間的權重縮放(例如降低格式 reward 的權重、避免模型過度擬合格式而忽略準確度);裁剪 loss 用的 epsilon / epsilon_high 與 loss type;以及策略更新用的 beta 與學習率,再加上每次生成的步數與 num_iterations,共同決定訓練有多「on-policy」。在解讀 Trackio 曲線時:較容易的 reward(如格式)應快速上升,較難的 reward(如任務成功率)應緩慢但穩定上升,熵值大致持平或略降,reward 的分散程度應呈現健康的變異而非完全打平。訓練停滯的跑法會呈現完全沒有 reward 訊號、也沒有任何分散;訓練崩潰的跑法則會出現熵值驟降、完成長度暴衝、某個 reward 被 hack 到頂、以及 KL/beta 因策略大幅偏離初始點而飆升。

Sergio 在 Hugging Face Jobs 上(無需本機 GPU)遞進地做了三組實驗,並全數用 Trackio 記錄。第一組刻意使用一個毫無意義的 reward——獎勵輸出長度接近 20 個字元——純粹用來示範 GRPO 會精準優化你所設定的目標,即便該目標本身毫無意義,reward 仍會持續上升。第二組在一個 Python 程式題資料集上訓練一個約 0.6B 的小型程式碼模型,以通過單元測試的比例(在有逾時限制的沙盒程序中執行)作為可驗證的 reward;基準測試顯示未訓練模型在多次生成下平均 reward 僅 0.22,並比較了 2、8、16 三種組大小,尋找 reward 既非全零也非全一的甜蜜點。第三組則刻意設計一個可被鑽漏洞的 reward——只要模型輸出四段 Python 程式碼區塊就給分,完全不管正確性——結果呈現典型的 reward hacking 現象:訓練 reward 一路衝上頂點,但保留的 test reward 卻持平不動,清楚暴露出「優化指標」與「真正解決任務」之間的落差。

問答環節的實務建議包括:訓練前先用文字樣本手動跑一遍 reward function;接著用少量步數與生成數做 smoke test,確認 reward 至少出現一些變異,再決定是否投入完整訓練;要讓能力出現有意義的變化,資料集規模有時僅需幾千筆樣本即可,儘管論文中常用遠大於此的規模;而要判斷模型是真正泛化、過擬合、還是在 hacking,需要同時檢視多條曲線與多個超參數(組大小、temperature、reward 組成),而非只看單一數字。下一場將把同一套 GRPO 迴圈延伸到完整的強化學習環境,屆時需要建構的不只是 reward function,還有 agent 所處的整個「世界」。
