---
title: 從 Agent 追蹤紀錄到 Agent 模擬環境
speaker: Rustem Feyzkhanov, Snorkel AI
---
這場演講主張，每家部署 agent 的公司都需要屬於自己的基準測試（benchmark）——而不是仰賴公開排行榜上的數字。這個基準測試必須貼近真實環境，模擬實際的工具、API、政策與工作流程，並且要持續從線上追蹤紀錄中補充資料，而不是建一次就凍結不動。

正式環境中的追蹤紀錄（輸入提示、採取的行動、輸出結果）對事後找出失敗案例很有幫助，但拿來做比較卻先天不足：每次針對真實系統重跑 agent，資料庫狀態、工具版本、環境都會不同，永遠無法做到真正的同條件比較。離線模擬則把追蹤紀錄轉化成可重複執行的任務，讓不同 agent 設定能在相同條件下重跑比較，評分標準不只是通過率，還包括成本、延遲與重試次數，並可平行執行。

像 SWE-bench、Terminal-Bench、OSWorld 這類公開基準測試，有助於掌握模型能力的前沿水準，但它們鎖定的是通用領域與工具。私有基準測試則反映公司實際的使用情境、政策與工具介面——這才是真正能夠上線的關鍵。模擬式基準測試能測試整個 agent 堆疊（模型選擇、思考預算、提示詞、執行框架、技能、工具），而不只是換模型比較，因為正式環境的表現取決於整個系統。

一個基準測試任務的結構，可參考 Harbor 這類格式：agent 看得到的指示檔案、環境（Dockerfile／Compose）、agent 看不到的 Oracle 解答與驗證器，以及中繼資料。Oracle 之所以重要，是因為它能在正式讓 agent 上場前，先證實任務確實可解。環境應該做到「迷你版正式環境」——具真實結構的資料庫、被模擬或以 sidecar 方式提供的 API 服務、以及模擬使用者（用 LLM 扮演人類）——使用快照而非完整正式資料，並透過多步驟結構與提前終止機制來處理長時程任務。

驗證不應只看最終輸出：可以檢視最終環境狀態、工具呼叫紀錄與完整追蹤，方法包括確定性檢查、LLM／agent 作為裁判，或針對性的領域專家審查——人工審查應保留給自動裁判意見分歧或出現真正邊界案例的情況，而非逐一審查所有結果。

基準測試任務可能以多種方式出錯：agent 察覺自己身處模擬環境而「作弊」得分、驗證器過於寬鬆（agent 永遠通過）或過於嚴苛（agent 永遠失敗）、或是同一任務重複執行時成功率極不穩定。既然基準測試本質上就是軟體，就該有自己的 CI 流程：鎖定相依套件版本、確認基礎映像檔正確、檢查是否缺少測試資料、跑 Oracle 解答確認任務可解、並透過多次 agent 執行為任務標註難度後才正式納入。

系統上線後，成熟的做法是建立兩個互相銜接的迴圈：一個是擴充迴圈，將可觀測性工具中發現的失敗案例納入不斷成長的基準測試；另一個是實驗迴圈，用新的 agent 設定重跑基準測試，並以「有可衡量、非倒退的改善」作為發布的把關條件。這種架構也能避免業界常見的反模式——把所有修正都塞進提示詞裡（「絕對不要做 X」）；透過對整個堆疊的掌控，你可以依問題的真正所在，選擇修正執行框架、新增技能，或強制規定結構化輸出格式。以這種方式建構的基準測試能一石三鳥：既是 agent 評估工具，也是發布把關用的整合測試，甚至能作為訓練資料，用來微調小模型使其在特定任務上媲美大模型。
