---
title: Evals 與 Prompt 如何形塑 Agent 行為
speaker: Preetika Bhateja 與 Daniel Bump，YouTube Ads
---
這場演講來自 YouTube Ads 團隊，該團隊打造用於廣告素材的圖像與影片生成 agent，內容提供了一套打造 eval 的實務作法，目標是讓 agent 真正可靠，而不只是「感覺上」可靠。演講的出發點是：agent 的可靠度是三件事的函數——底層能力、guardrail，以及 eval；而 eval 唯有在基礎穩固之後才會真正有效：應先優化一組聚焦、對 LLM 友善的工具集，並用一個獨立的 critique agent 搭配修正迴圈來補足基礎工具的不足，之後才值得投入建置完整的 eval 體系。

一個違反直覺卻很重要的早期建議是：「憑感覺（vibing）」——也就是非正式、不可規模化、靠直覺去檢視輸出——在初期其實很有價值。它讓小團隊能快速看出失敗模式，並在不被僵化 eval 綁手綁腳的情況下對 prompt 或架構做出大幅調整，藉此累積後續設計真正 eval 所需的深度理解。若太早跳到大規模的 rater 評測，反而會造成品質忽上忽下的雜訊，因為團隊等於同時在校準 rubric 和模型。

Eval 應該從小處著手：先挑出幾個 agent 必須做好的核心任務，並且同樣嚴格地測試「負向情境」——確認 agent 不會做出不該做的事——因為撰寫 eval 本身往往很快，真正困難的是團隊對 rubric 達成共識。當投入規模擴大到跨職能團隊和外部 rater 時，幾項作法被證實很重要：提供明確 rubric 與具體範例，以減少模糊邊界案例與意見分歧；並且務必在 pass/fail 判斷之外收集解釋，因為單純的結論無法說明「為什麼」失敗，或在多輸出、多輪的評測中（例如準確度 vs. 品牌安全）究竟哪個面向較弱。

在使用 LLM-as-judge 的情境中，團隊追蹤 LLM judge 與人類／專家 rater 之間的一致率，藉此持續校準；同時不滿足於單純的 pass/fail，而是深入檢視 agent 實際的推理軌跡（trace）。一個具體案例說明了原因：agent 被多次明確要求「基於法規理由絕不可移除廣告中的免責聲明」，但單看 pass/fail 指標無法抓出某些邊緣案例中它仍然移除了免責聲明的情況。唯有透過閱讀 trace，團隊才發現 agent 明確推理出「我找到了免責聲明，現在要把它移除」——這種失敗若不深入 trace 層級是看不到的。

傳統機器學習的經驗依然適用：agent 對訓練與測試分布之外的情境泛化能力有限，因此維持一組保留的測試集來檢驗邊緣案例與更廣泛的能力仍有價值，但應謹慎使用，並定期以生產環境資料更新，以避免對其過度擬合。

品質的爬坡過程是一個反覆的迴圈：先做人類評測，若未達標準，就深入檢視 eval 資料集上的 precision/recall，接著調整 rubric、模型，或是 agent 的工具配置，然後重複此過程。至於上線準備，團隊需要找出效能退步的原因與位置，區分可接受的取捨與關鍵性失敗——更重要的是，不要過度聚焦在單一失敗案例上，因為這些系統本質上是非確定性的；真正重要的是某個失敗模式在具代表性的黃金資料集中出現的頻率，而非單一一次的執行結果。持續投資能反映真實資料分布的 online eval，同樣至關重要。

結尾的總結是：好的 eval 系統應該真正反映產品需要在哪方面表現出色，而這會隨著 agent 從 MVP 走向正式上線而改變。它必須透過 online eval、定期更新的測試集與抽樣管線持續演進；仰賴經過高度審核、不斷更新的黃金資料集；明確訓練 rater 與跨職能團隊了解評分期待；提供清楚的 rater 範本與附範例的 rubric，避免出現模糊的「不確定」判斷；並及早訂定具體的上線／把關指標，因為不同使用情境所需的合格門檻（precision/recall 或其他指標）並不相同。
