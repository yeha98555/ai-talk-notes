---
title: 你的 Agent 沒有失敗，是你的 Harness 失敗了
speaker: Vinoth Govindarajan, OpenAI
---
這場演講的核心論點很直白：絕大多數正式環境中的 agent 失敗，並非模型失敗，而是 harness（外圍系統架構）失敗。開場案例是一種「靜默成功」——使用者要求 agent 記錄一筆退款，助理確認已記錄，介面看起來一切正常，但下一輪對話卻完全沒有這筆事實的持久紀錄。當機至少給你一個明確邊界，讓你能從最後已知的良好狀態重新開始；但靜默成功給你的是一個謊言，因為模型依然流暢、連貫地回應，即便它是基於一段殘缺的歷史在推理。

講者任職於 OpenAI 核心資料與 AI 基礎架構團隊，將整場演講建構在一個「生產契約」之上：模型提出建議、harness 執行提交、receipt（憑證紀錄）加以證明。模型可以建議一則訊息、一次工具呼叫、一項編輯或一個指令，但模型本身不是生產環境的邊界——狀態轉換、權限檢查、有序提交，以及能撐過這一輪對話的憑證紀錄，都屬於 harness 的職責。整場演講大量引用 OpenClaw 公開的 issue 追蹤紀錄作為案例研究，純粹是因為其 harness 問題異常清晰可見，並非產品推銷。

一個汽車類比奠定了整體心智模型：模型是引擎，但光有強大引擎造不出一輛能上路的量產車——你還需要方向盤、煞車、交通規則、儀表板和黑盒子。一個沒有煞車的強力引擎不是自主性，而是加速性能很好的一種負債。跨個人助理型 agent 與程式編碼型 agent 共通的 harness 藍圖是：事件從多種介面（聊天、webhook、計時器、心跳）進入；控制平面將每個事件映射到一個 session key，此 key 界定了一個狀態邊界，且該邊界只有一個活躍寫入者；runtime 呼叫模型與工具；工具透過核准與政策機制執行動作；稽核軌跡最終形成這次執行的憑證。由於 runtime 本身是無狀態的，harness 必須在每一輪對話中重新組裝完整的工作集——對話紀錄、session 狀態、記憶、政策、工具定義——一旦其中某項輸入缺漏或過時，模型的回答仍可能聽起來很合理，但實質上是錯的。

這些底層失敗類型其實都不新，逾時、重試、冪等性、鎖、排序、狀態所有權，全是經典的分散式系統問題。真正改變的是場景：如今這些失敗環繞著一個會動態產生計畫的機率式規劃器，涉及更多事件來源，也能透過更多動作介面採取行動，這使得它們更容易被觸發，也更難被解釋清楚。

演講中列舉五種具體的失敗型態，皆取材自真實的 OpenClaw issue。第一，狀態空洞：一則已送達的回覆不等於一項已被記住的事實——所有權意味著必須有一個具名的紀錄系統能夠回放（replay）該事實，光憑資料存放位置本身無法確立這一點。第二，寫入者重疊：在「讀取—修改—儲存」的競爭條件下，兩次各自局部正確的寫入仍可能產生一個錯誤的結果，因為「後寫入者獲勝」並不是一種一致性模型；解法是為每個可變狀態邊界建立單一有序提交路徑，而非消除並行性本身。第三，懸置的工具呼叫：一次執行可能永遠等待一個永不會到來的工具結果，因此每個外部邊界都需要期限、看門狗（watchdog）、取消機制，以及一個被記錄下來的終止結果——成功、失敗、逾時或取消。第四，核准漂移：能力不等於執行權，一項核准必須是一個被限定範圍的執行狀態，並綁定到執行者、session、工具、參數與有效期限，過期後應該終止，而不是靜默地重複循環。第五，缺失的邊界證明：工具回報內部成功，並不能證明使用者確實看到了結果，因此證明必須是一條完整的鏈——模型提案、政策決策、執行嘗試、以及經確認的使用者可見結果——而非單一的一句宣稱。

演講最後提出一套五問稽核法，可套用在任一條真實正式環境的執行紀錄上：是什麼喚醒了這次執行、它繼承了什麼狀態、它使用了什麼權限、它實際執行了什麼、以及有什麼證據留存下來。把這套方法套回開場案例：觸發來源是一則使用者訊息，它繼承的狀態正是那個被打破的邊界，管道發送已執行且訊息已送達，但持久化的對話輪次卻沒有留存——這個缺口不是靠更好的模型或更好的提示詞能修補的，只能靠一個具備完整憑證紀錄的更好的 harness 來解決。結論濃縮成三句話：擁有狀態的所有權、為變更排序、並證明每一個動作。
