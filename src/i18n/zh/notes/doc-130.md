---
title: 打造程式碼編輯 Agent：國王的新衣
speaker: Jeff Huntley, Sourcegraph (AMP)
---
這場演講的核心主張是：程式碼編輯 agent 並沒有什麼神秘之處，本質上就是約 300 行程式碼跑在一個迴圈裡，不斷把目前為止的對話送給 LLM 做推論，再檢查模型是否想呼叫某個工具。Claude Code、Cursor、Windsurf、GitHub Copilot、AMP 等工具全都建立在同一個迴圈原語上；工具供應商在其上添加的，主要是一些小提示（你在 macOS 上、用正斜線、用 PowerShell）以及 prompt 調校，但真正做大部分工作的其實是模型本身。講者現場從零開始、循序漸進地打造出一個 coding agent 來證明這一點。

第一個關鍵概念是：並非所有 LLM 都同樣「agentic」。可以用一個四象限來對模型分類：一軸是安全對齊程度，一軸是主動呼叫工具的傾向。像 Grok 這種低安全性模型適合資安研究；Anthropic 或 OpenAI 這類高安全性模型適合對倫理敏感的工作；像 o3 這樣的「oracle」模型擅長總結與高階思考，但不太願意採取行動；而像 Claude Sonnet 這類模型則像隻興奮的小松鼠，一直想去呼叫工具。單純以價格和 context window 大小來比較模型，就像只看車門數量來評比汽車，卻忽略了有些車是設計來越野、有些是用來載人的。把不同模型組合使用能發揮各自優勢，例如用 agentic 模型做事、用 oracle 模型來檢查結果。

第二個關鍵概念是嚴格管理 context window。同一時間應該只專注在單一活動上——把不相干的任務混在一起（例如新增一條路由 vs. 幫網站改頭換面）會造成「大海撈針」式的混淆，實務上的解法就是每個任務都開新對話。context window 也比看起來要小得多，因為系統提示與工具定義本身就會佔掉不少空間，而每註冊一個 MCP server，就會多一個描述如何呼叫它的「廣告看板」，進一步佔用預算，甚至會讓模型明顯變笨。建議是不要不分青紅皂白地啟用一堆 MCP server——基礎模型通常已經訓練過標準 CLI（例如 GitHub CLI），除非真的是 server 對 server 的整合，否則不需要專用的 MCP。

現場實作展示了組成一個真正 coding agent 所需的最小原語，並逐層堆疊：一個完全沒有工具的純聊天迴圈；一個天氣查詢式的函式呼叫，用來說明工具或 MCP 其實就是「一個掛著廣告看板的函式」，看板上寫著 LLM 該如何呼叫它；一個 list_files 工具，讓 agent 能看見專案的檔案結構；一個 read_file 工具，讓它能把特定檔案內容讀進 context（示範方式是讓它從一個文字檔中解一則謎題）；一個 bash 工具，用來執行系統指令（示範總結 CPU 使用率最高的行程）；最後是一個 edit 工具，結合前面所有工具，讓 agent 能搭建一個小型 Node/TypeScript FizzBuzz 應用、執行它、驗證輸出，並在後續指令下修改它。每個原語都刻意設計得很小、可組合，而觀察到的工具呼叫失敗案例，正是工具團隊用來調校系統層與工具層 prompt 的依據。

演講的結語比較偏文化層面而非技術層面：從第一性原理理解如何打造 agent，正逐漸成為工程師的基本素養，就跟知道什麼是 primary key 一樣重要，因為這能讓人從 AI 的使用者變成 AI 的生產者，進而在自己的領域中自動化真正的工作職能（講者提到一位工程師運用這項知識，自動化了原本需要二十人完成的工作）。被 AI 取代的風險並非來自 AI 本身，而是來自沒有投資這項技能。並非所有問題都該用 agent 解決，但親手打造一個 agent，能培養出判斷力：什麼時候可以放心讓它自主運作、什麼時候需要人在迴圈中把關，以及一連串 agent 對 agent 的呼叫鏈能承受多少「跳數」而不會讓結果品質下滑。
