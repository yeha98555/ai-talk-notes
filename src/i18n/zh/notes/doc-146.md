---
title: Harness Engineering:打造 AI 軟體工廠
speaker: Dru, Tessl
---
這場演講介紹「harness engineering」(也被稱為 loop engineering、meta engineering,或建構軟體工廠),主張這是一種新興的工程方法:與其自己寫程式碼、或盯著 agent 寫程式碼再修正錯誤,不如去建構並監控那些能讓 agent 自行撰寫、審查、維護程式碼的迴圈。軟體工廠的終局狀態是:一套 agent 系統從頭到尾打造出交付給使用者的產品,而人類則專注於規劃工單、任務,並持續提升系統的自主性(autonomy)、自動化程度(automation)與品質(quality)。

這趟旅程圍繞三項指標展開。自主性指的是 agent 要達到正確答案需要多少次人類糾正——可用人類發言輪次或 PR 留言數來衡量。自動化程度指的是即便 agent 已經很自主,仍需要多少人類監督;許多團隊已解鎖自主性,卻仍卡在審查瓶頸,因為信任還沒建立起來。品質則單純是:當更多工作交給 agent 之後,產品交付出來是否依然夠好。

打造軟體工廠的理由不只是速度。速度最先見效也最快見效,但更大的轉變在於品質:agent 是不知疲倦的程式碼審查者,審查能量不再受限於人類的耐性,而在採用進度較領先的公司中,已經觀察到隨著審查投入擴大,bug 數量反而下降。另一方面,現今大多數 bug 其實早已被發現,只是長期被壓在待辦清單底層、永遠排不到優先順序;一旦產能大幅提升,待辦清單基本上會消失,過去被忽略的小眾問題也終於能被修好。軟體工廠同時打破了「誰能寫程式碼」的門檻——來自業務、設計、甚至人資部門的人都能送出上線的 PR;而在講者看來,剩下要做的工作(架構設計、系統設計、如何隨時間擴展)其實更有趣,這也是他即使速度、品質、人員都不變,依然會選擇以工廠模式工作的原因。

打造軟體工廠不是一次性的推倒重來,而是漸進式的過程——找出一個工作流程,把它包裝成 agent 能理解的形式,先互動式跑幾次建立信心,再逐步自動化,一次做一個工作流程。真正該問的問題不是「該不該建工廠」,而是「你想成為百分之多少的工廠」。

Harness engineering 本身圍繞三種迴圈組織。內迴圈(inner loop)驅動自主性:單元測試、linter、手動檢查,agent 據此反覆爬坡再送出 PR——由於這些測試套件現在由 agent 自己維護,團隊可以比以往對人類嚴苛得多。外迴圈(outer loop)驅動自動化程度:較慢、較深入的檢查,例如 agentic 程式碼審查,或讓 agent 實際點擊執行中的產品並截圖,建立起「不必事事人工檢查」的信心。元迴圈(meta loop)則是把前兩種迴圈自動化運轉:agent 會掃描一週份的 CI 失敗紀錄或 PR 留言,找出反覆出現的錯誤,並提出新的 lint 規則、skill 或測試——這是最終大部分時間會花費的地方,因為它把被動救火轉變成審核建議。

Harness engineering 困難的原因主要是組織性的,而非技術性的。最佳實踐不斷變動,跟上腳步本身就不是任何人的本職工作。面對 agent 出錯的正確做法是丟棄該 PR、找出原本該有哪個檢查或 skill 能防止此錯誤、修正後重試——這感覺像是計畫外的工作,而且當「兩小時前本可直接修好」時,這個決策很難對外交代。可見度(legibility)也很差:團隊往往要靠零星對話才慢慢意識到大家其實都在踩同樣的坑。

幾項具體元件讓這一切變得可行。槓桿最高的單一改變,是從互動式、單次對話的 agent 工作模式,轉為以工單與 PR 為主的工作流程——工單與 PR 留言成為 agent 與人類共用的可見介面;據稱 OpenAI 完全轉向此模式後生產力提升了五倍。在此基礎上,團隊很快會累積大量 playbook 與 skill(一週內從五個暴增到上千個),這促使團隊建立 skill 註冊表——類似 npm,用來分享、版本控管,並讓改進自動惠及所有人。早期大量心力會投入「讓一切對 agent 友善化」:給 agent CLI、雲端沙盒環境,以及讀取「公司大腦」(Slack、文件、內部服務)的權限,避免卡在只有人類能登入的服務上。最後,改進迴圈把整個系統閉合起來:維護型 agent 會掃描近期的日誌、工單與 PR 留言,提出修正或新的自動化,低風險區域可自行合併,涉及正式環境的則交由人類審查。

Tessl 將自身定位為打造這類工廠的平台:內建 agent 介面持續追蹤最佳實踐的變動、程式碼審查邏輯以純檔案形式存放於 repo 中而非黑箱、附帶評測與安全檢查的 skill/plugin 註冊表、預設的 GitHub/Linear 整合,以及所謂的「verifier」——小型、便宜、由 LLM 驅動的類 lint 檢查(號稱以 100 多個 verifier 跑完一整天份的 PR 審查僅需約 0.3 美元,相較於一次完整 agentic PR 審查約需 25 美元),藉此把審查左移進內迴圈。變更風險分析器(change risk analyzer)則依團隊議定的品質政策掃描每個 PR,判斷是否可自動合併或需要人工把關。

結尾建議在軟體工廠成熟過程中追蹤幾項關鍵數字:降低人工介入次數(人類的 PR 留言、手動拆解工單),提高由維護型 agent 自動發起的 PR 佔比,並持續提升——而非僅僅維持——程式碼品質,這首先意味著要先解決「品質該怎麼衡量」這個難題,而不是以品質換取速度。
