---
title: 規格驅動開發的經驗教訓
speaker: Simon Martinelli
---
這場演講從一個小故事開場：作者在 2024 年底用 Windsurf 為瑞士一個運動俱樂部打造志工管理系統，起初順利，但當第二個組織提出相似卻不同的需求時，他發現自己對已建成系統缺乏清楚的紀錄，也不知如何調整——這正是他走向規格驅動開發的契機。他的做法與多數工具廠商不同，因為他日常處理的是企業級商業應用（保險、批發零售、政府單位），而非從零開始的產品。

他將自己這種以流程為核心的做法，與 Amazon Kiro、GitHub Spec Kit、BMad 等以工具為核心的規格驅動方法區分開來——後者都是把產品需求文件轉成計劃，再拆成任務交給 agent 執行。他自創的「AI Unified Process」則完全跳過計劃／任務階段：系統使用案例（一種源自 1987 年、後經 UML/RUP 精煉的規格格式）搭配實體／領域模型，直接餵給 agent 產生程式碼與測試。使用案例包含角色、前置條件、後置條件與主要／替代情境，他認為這比使用者故事表達力更強（一則使用者故事本質上只是使用案例中的一條流程），而且由於此格式歷史悠久，模型早已能很好地讀寫這種格式。

在全新專案中，需求工程師與業務分析師負責產出使用案例與實體模型，經過完成定義的審查後，才由配備了特定技術棧技能、MCP 伺服器與護欄的 agent，依情況（API 先寫測試、有 Figma 設計則先做 UI）直接產生程式碼與測試。但他實際大部分工作是現代化改造而非新建系統，流程因此反過來：從既有程式碼、測試與零散文件中反向工程出使用案例與實體模型，經業務利害關係人審查後，再據以在新技術上重新生成系統。他強調這並非單純的搬移轉譯（他提到早年 COBOL 轉 C 之類的做法已證實失敗），因為規格一旦明確化，團隊便能刻意修正或擴充行為，而非把舊系統的錯誤原封不動地搬過去。

現場示範將 Spring PetClinic 範例應用反向工程為使用案例圖、實體模型與詳細使用案例文件，接著僅用一句「implement」指令，依賴預先建好的技能，端對端重新生成某項功能——過程中沒有臨場拼湊提示詞。其可靠性來自幾項護欄：絕不讓 agent 自行從零建立專案（改用框架自帶的 CLI／初始化工具，避免依賴版本過時）；保持系統提示檔（如 CLAUDE.md 或 AGENTS.md）精簡，蘇黎世大學的一項研究發現系統提示越長，幻覺可能越多；把大部分指引放進版本化、持續迭代的技能與由 MCP 支援的文件／向量搜尋中；並依受影響模組的業務風險高低，調整所需的人工審查強度。

架構選擇對此流程的成效影響甚大。過度切碎的微服務（某客戶有約 500 個服務與約 500 個微前端）會把上下文分散到太多儲存庫，agent 難以一次掌握全貌；而反過來走向單一巨型單體，只是把同樣的問題搬進同一個程式庫裡。他偏好的折衷方案是「自足系統」（self-contained systems）風格——與早期微服務同時期出現的架構——將應用切成垂直切片，每片各自擁有 UI、商業邏輯與資料庫，且理想上每個切片只用單一技術棧，避免前後端生態系各自重複建立技能。

這套流程也改變了團隊組成：自足系統通常僅配置一到兩名開發者（偏好兩人以利知識交流），而非五到七人；衝刺（sprint）讓位給以使用案例看板追蹤的持續流；程式碼審查則變成持續的結對審查而非提交合併請求，因為主幹式開發搭配快速、近乎確定性的生成，使冗長的審查佇列變得不必要。

他最後指出，光有規格並不足夠——還需要技能、護欄與架構所構成的整套支撐環境——但規格具有持久性：由於行為現在存在於使用案例與實體模型中，而非程式碼本身，同一份規格理論上可以在不同技術上重新生成應用程式，甚至完全不需要 UI，讓業務人員無需開發者介入即可調整系統行為。目前實際的效果是工作重心向左移：需求與規格工作如今佔去大部分行程（他舉一個政府案件管理系統專案為例，兩位全職需求工程師支援一位負責實際生成工作的開發者），而實作階段則大幅壓縮——前提是團隊要真正深入理解自身的架構與領域。
