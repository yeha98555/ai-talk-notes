---
title: 每個問題都有代價：為 Agent 重建資料堆疊
speaker: Ethan Ding, TextQL
---
這場對談的核心論點是：AI 讓資料與商業邏輯在不同系統間的搬遷成本趨近於零，這直接動搖了現代資料堆疊的根本前提——如果不再需要把一切集中搬進 warehouse 或 lake 才能使用，就可以直接連到每個資料來源系統原本所在之處，並在第一天就讓它們彼此可互通。這個想法源自親眼見證企業耗費多年把同一套商業邏輯從 Redshift 搬到 Snowflake 再搬到 Databricks，也源自共同創辦人的高頻交易背景——在那個領域，勝出的公司永遠是花最少時間清理資料、花最多時間把資訊轉化為可執行決策的公司。

現代資料堆疊被形容為一條 1970 年代的裝配線：從 ETL 進 warehouse、資料建模、語意層策展，到最終儀表板消費，每個階段都需要人工介入，每次交接都增加延遲。TextQL 的 agent「Anna」被設計成能直接跨 ERP、CRM、EHR、warehouse、資料庫與 BI 工具運作，而不是綁死在單一平台上；同一個 agent 能在 Tableau 建立儀表板、把計算欄位推進 dbt、更新 warehouse 的資料擷取管線，並可在地端部署，在一個下午內串接橫跨多個雲端的數百個資料庫。由於現在生成一份儀表板只需約 30 秒，論點主張大多數儀表板應該變成用完即丟、即時產生的產物，而不是為了攤提建置人力成本而長期維護、層層治理的物件。

「髒資料」被重新定義為一個已解決的問題，而非阻礙。與其讓每個新指標都經過為期三週的治理委員會審核，TextQL 讓商業使用者可以先在本地自訂指標並「記住下次要用」，這會對存放語意層的 GitHub repo 產生一個 pull request；資料團隊再批次審查這些提案。在 agent 帶來的請求量下——每月數萬筆資料請求——治理必然從逐一稽核每個指標，轉向掌握方向性正確：分析哪些查詢與資料表最常被重複使用，並將其正式化為「黃金指標」，這被認為比委員會制定的定義更可持續，因為後者常常被使用者繞過、直接匯出到 Excel 了事。

分析的準確度被放在期望值（EV）、類似交易的視角下理解，而非追求絕對精確。決策迴圈的設計目標是花幾美元的 token 與運算成本，換取價值高出一個數量級的結果，透過跨資料來源取樣來提高信心水準，而非要求百分之百確定——舉的例子是：對一筆十萬美元的理賠案，若信心水準達 95% 判定為詐欺就直接拒賠，願意承擔 5% 的誤差，因為進一步查詢的成本已超過邊際準確度的效益。某些領域，例如 FP&A 的結帳流程，仍需要接近完全準確，但許多企業決策只需比現狀好上幾個百分點,就能在大型金融服務與保險場景中釋放出可觀的損益影響。

在鎖定（lock-in）這件事上，TextQL 刻意不靠儲存或席位收費——這正是多數供應商（如 Tableau、Databricks）用來把客戶綁在自家平台上的模式。情境、記憶與語意層 YAML 都存放在客戶自己的 GitHub repo 中，作為客戶自有的智慧財產；其主張是供應商唯有持續擴大客戶能查詢的資料範圍才能獲利，因此必須不斷保持最佳選項，而非仰賴轉換成本。這也是為何單純把通用型 coding agent 丟到 warehouse 上並不足夠的原因：一開始效果不錯,但很快會在跨多個資料庫的角色╱欄位層級權限控管上碰壁,語意層也沒有持久的歸屬,而最尖銳的問題是失控的成本——商業使用者會從問「這個數字是什麼」升級到「為什麼」,再到「告訴我下一步該怎麼做」,常常把單次查詢變成每小時執行一次的排程任務。TextQL 的優化方向則是讓每一次後續查詢更便宜——採用類似協同過濾的方式優先處理常被存取的資料表,並實質上將常被大量彙總的視圖物化——使每筆查詢的中位數成本隨使用量增加而下降,而非隨之上升。

給資料領導者的建議是:掌握自己的儲存、商業邏輯與運算引擎,不要把基礎設施整套租給綁定單一 warehouse 供應商的平台;並讓整套堆疊對 agent 友善——以檔案形式呈現:儀表板變成裝有 SQL 與 JavaScript 的資料夾,語意層變成存放在 warehouse 之外的無頭檔案,schema 則採用像 Iceberg 這樣的開放表格格式,透過無頭查詢引擎存取。急迫性在於:warehouse 查詢量即將爆炸性成長——TextQL 在部分客戶端已佔淨新增 SQL 查詢量的約 75%——而 warehouse 帳單,作為 LLM token 支出的互補品,即將以企業尚未編列預算的方式暴增。

被問到對未來 18 個月的預測,他認為大多數企業 SQL 將由 AI 撰寫,而其中大部分將來自商業使用者以「有問題的方式」提示 AI,需要積極的引導與塑形來修正。目前佔資料庫查詢總量不到一成的公民資料科學家查詢,可能會攀升到 70% 到 90%,這將考驗那些原本未曾為此規模設計的資料倉儲架構,並要求在複寫與成本管理上採取全新做法。
