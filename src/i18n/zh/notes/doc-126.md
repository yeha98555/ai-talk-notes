---
title: 真正可行的資料合約(Data Contracts)
speaker: Peter, Audax
---
這場演講從一個資料工程師都很熟悉的痛點談起:資料管線幾乎每天都會出問題,有時候還是無聲無息地壞掉,而根本原因往往是團隊只把 schema 當成整份合約,但 schema 其實只是管線所依賴 metadata 中很小的一部分。資料的生產者(producer)可能改變某個欄位的計算方式、是否允許為 null、是否唯一,或是資料延遲到達的時間,而這些變動完全沒有被記錄下來,只存在建置管線的人腦中。消費者(consumer)只能被動承受上游的改動,而他們與生產者之間唯一的橋樑就只有一份 schema。

解法是透過資料合約把這些隱性知識明確化,讓生產者與消費者之間的協議變得可執行(enforceable)、可測試(testable)、可自動化(automatable)、可共享(shareable),而不只是一份描述性文件。這正是 Open Data Contract Standard(ODCS)的初衷——一個廠商中立的開放標準,目前隸屬於 Linux Foundation,最初由 Jean-Georges Perrin 從 PayPal 帶出,並由一個志願組成的技術指導委員會持續發展。其核心理念是把資料當作 API 來對待,如同 OpenAPI 之於 HTTP API 一般:一份共享、與工具無關的規格,讓生產者、消費者、業務分析師、產品負責人都能讀懂、依此驗證,並在其上建構工具。

ODCS 合約涵蓋的範圍遠不止欄位名稱與型別。它包含限制條件(nullability、唯一性、數值範圍、自訂 SQL 或資料品質引擎規則)、擁有者與聯絡資訊、跨版本的相容性與版本控管、資料新鮮度與到達時間的 SLA,以及安全性與存取權限規則,同時也定義邏輯型別與實體型別的對應,讓同一份合約能描述存放在 Postgres、Iceberg 等不同系統中的資料。由於所有 metadata 都集中於一處,合約便成為單一真實來源(single source of truth),可由此衍生出許多下游產物:告警規則、監控設定、樣板程式碼、測試、文件、資料保留政策,甚至可匯出到任何團隊採用的資料目錄工具(如 Collibra、DataHub 等),而合約到工具之間的映射只是一層薄薄的轉換層,而非遷移工程。

實務上,以輕量 YAML 檔呈現的合約可以自然融入 CI/CD 流程:能自動驗證、能用來產生近似正式環境的合成測試資料,讓管線在不碰觸真實正式資料的情況下被測試,也能在部署前攔截違反 schema 或規則的變動。在治理層面,講者的主張是與其讓治理團隊只在資料目錄的 UI 上點按鈕、流程到此為止,不如把治理規則直接寫入合約本身,使其具備可執行性,並可攜帶到組織所採用的任何目錄或品質工具中。

關於導入方式,建議從小處著手——挑選一條最讓人頭痛的正式環境關鍵管線,把散落在信件往來與分析師腦中的隱性知識蒐集起來,編碼進合約中,再逐步迭代,而不是一開始就推行全面的 data mesh 策略。資料合約並不被當作每個團隊都必須採用的東西,其價值應視具體情況評估。理想的終局狀態是生產者與消費者之間不再有隱藏的假設,雙方期望一致,一旦出問題也能減少互相指責,因為合約本身就像一份法律契約,能直接釐清爭議。

聽眾提問也補充了不少實務細節。合約的執行是雙向的:生產者可以測試自己輸出的資料是否符合合約,消費者也能驗證收到的資料是否符合合約,任何分歧理論上都應該在合約制定當下就被發現並解決。目前已有工具可將此理念落地——開源的 Data Contract CLI 能讀取 ODCS 的 YAML 檔,並產生 SQL、Soda 資料品質規則等多種產物,ODCS 的 GitHub 上還列有更多相關工具。至於告警疲勞(alert fatigue)問題,講者坦言資料合約並不能直接解決它,但可以為資料品質規則加上分類標籤(如一致性、唯一性、新鮮度等),讓團隊即使定義了成百上千條規則,也能篩選出真正需要觸發告警、值得採取行動的那一小部分。
