---
title: Factory 如何實踐 Forward Deployed Engineering
speaker: Eno Reyes, Factory
---
作為 forward deployed engineering 專場的開場，Eno Reyes 從 Palantir 時代的打法談起——當年因為整合工作只能在客戶環境「簾幕之後」進行，必須把強悍的工程師空降進客戶組織——並指出這個角色如今已分岔成幾種界線模糊的變體：替客戶代工的專業服務、圍繞單一客戶改造產品，或在客戶環境裡從零打造全新系統。Factory 對第一種劃下明確紅線：當客戶拿著顧問公司的報價，要求 Factory 代為執行 codebase 現代化時，答案是拒絕——即便會用到自家產品。代工收入不差，但既不會讓產品變好，也撐不起可大規模擴張的生意。

相反地，deployed engineer 是「產品的矛尖」：他們是來自最大、最關鍵客戶的資訊流——工程領導層的想法、第一線工程師的實況、軟體開發與 AI 在該組織實際運作的方式——把這些回流進產品，快速調整產品去貼合客戶環境。目標是讓 Factory 在客戶環境中有效地「自我組裝」；當客戶有 45,000 名員工、可能數十萬工程師、上萬個 codebase 時，這不是奢侈而是必需——這種複雜度不可能靠人工安裝。

Factory 賣的東西被描述為打造「軟體工廠」的積木，其基礎是每個組織其實都已隱含運行的流程：外界訊號流入——客戶對話、bug 回報、內部 Slack 或 Teams 討論、高層拍板——由人排序、分流並擬定計畫，開發者把計畫轉成對單一事實來源的變更，變更經過驗證階段（code review、QA、資安評估、SAST 工具、linter、型別檢查），最後部署上線，而上線的軟體又產生新的訊號。多數組織對這個回饋迴圈的儀表化做得很差；若用 AI 改造每個階段、並理解各階段之間的工作流，就能達到「從訊號到部署全程不被人打斷」的境界——這不代表沒有人類參與，而是人類負責打造這套系統，而非站在迴圈中間。這是「用蓋的，不是用買的」（built, not bought），而平台的賣點是為此準備的標準化、模型無關的 agent harness：Droid 提供模型獨立性、對流經其中的每筆 trace 與資料的完整所有權、企業層級的集中治理，也可以完全 air-gap——金融、醫療、政府等最高安全等級的合作夥伴就以完全隔離的方式運行軟體工廠，一位 deployed engineer 甚至開玩笑說你可以把 Droid 跑在潛水艇裡。

在這個脈絡下，deployed engineer 的工作有三重：讓產品能在客戶環境自我組裝；教會組織一套轉型模型——多數組織根本沒有自主性成熟度模型，也沒有邁向自主軟體組織的路線圖；以及從一開始就建構清楚的 ROI 敘事，例如經過 AI code review、QA 與資安分析的變更遇到 bug 的機率降低約 87%，從而降低 bug 率、提升客戶滿意度、最終反映在營收上。在這個世界裡，工程師從直接操作軟體，升級為維護與管理一套「會打造軟體的系統」；這種抽象層級的躍遷連思慮縝密的工程師都覺得困難。最適合的人選是早已在思考開發者賦能的 DevEx 工程師、願意快速變得非常技術的產品經理，以及在重視高品質開發環境的團隊中歷練過的人。

其中很大一部分工作是讓 codebase 具備 agent-ready 條件；Reyes 將其定義為「codebase 內決定性驗證迴圈的數量」——回饋迴圈越多，agent 就能在越複雜的任務上長時間自主運作。Factory 的工具會掃描缺口，約 30–40% 的低垂果實真的只要一句「Droid，把這些全修掉」；其餘 60% 則涉及工作流改變，以及照顧那些還不習慣自動化驗證「吹毛求疵」程度的人。終局形態的 harness 是「missions」：除了規劃階段外幾乎沒有人為介入的長時間運行——定義一個有邊界的任務與「完成」的判準，然後「壓下推論的閥門直到任務完成」。只要「完成」是可驗證的，這種做法的能力驚人：全自主遷移三、五千萬行以上的 codebase、生醫領域的深度學習研究、金融機構的股票研究系統。從模型訓練的角度看毫不意外——模型是在密集獎勵上做後訓練的，而組織的驗證訊號正是讓長時程 agent 不偏航的獎勵來源。因此 deployed engineer 給客戶的建議聽來反直覺：少投資在解決問題本身，多投資在讓環境能「驗證」問題。

至於第一個部署點之後如何擴散，Reyes 引用華特迪士尼的 EPCOT 為喻：一座可運作的「未來城市」範例會被其他城市借鏡——但蓋得太超前，就成了沒人相信能套用到現實的主題樂園。未來在今天分布不均：Factory 自家 codebase 的自主比率已在八成後段，某些客戶因運作方式更受限反而更自主，而最先達到 100% 的會是高度受控的內部工具——Factory 的「legal droid」法務工作流已完全自主維護，核心 harness 卻還不行，因為終端機閃爍這類困難的視覺問題仍缺乏可驗證的檢查。他認為，為「目前只有人類看得出來的問題」打造驗證器，正是人類接下來的工作樣貌。結尾的招募喊話：曾經創業的人（Droid 涵蓋的每個 SDLC 階段——code review、事故應變、QA、測試——都是十億美元等級的生意）、能對各層級溝通、具商業敏感度與高層溝通力的技術傳播者，以及熱愛封閉迴圈與建模資料流的系統思考者，都是最能勝任這個角色的人。
