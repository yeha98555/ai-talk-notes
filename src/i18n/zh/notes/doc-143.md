---
title: From Signal to PR：自我改進代理的解剖學
speaker: Jason Lopatecki, Arize
---
這場演講主張，可觀測性（observability）正從以人為中心的模式——儀表板、圖表、需要人去點擊查看的東西——轉向以機器為中心的模式，遙測資料成為讓代理（agent）得以自行除錯並修復軟體的「排放物」。講者以 Arize 自家打造的產品內代理 Alex（第一版「說實話很爛」）以及其後繼系統 Signal 的經驗為例，Signal 試圖將團隊每天尋找並修復生產環境問題的例行工作自動化。

演講的框架是「可觀測性 2.0」：建立在可觀測性平台（Pyroscope、Grafana 等）之上的 skills，讓一個編碼代理能夠取得它所需要的確切上下文——traces、logs、錯誤路徑——就像人類手動除錯時使用這些工具一樣。沒有這些遙測資料，代理只能在數百萬條可能的程式碼路徑中猜測；有了它，代理便能看清系統實際走過的路徑。Evals 則在原始 traces 之上再加一層，本質上是可供除錯代理消費的預處理訊號。

關鍵的一步是把傳統迴圈反轉過來：不再是人類先發現問題再指示代理去修，而是代理先發現問題——在人類都還沒看到之前，就先附上證據把問題浮現出來。這使得工作性質從「回應者」轉變為「審閱者」，也讓真正的瓶頸從「寫出修復方案」轉移到「確信這個修復方案是對的、可以上線的」。如今，一旦線索被浮現出來，人類往往仍主導後續更深入的調查，但即便如此，這份調查也是從遠比以往紮實的證據基礎出發。

就結構而言，這個迴圈包含三個部分：觸發（週期性或事件驅動，例如錯誤發生）、透過 skills 收集上下文（把 logs/traces 拉下來，往往是以檔案形式，有時甚至數十 MB，直接放進 repo 裡）,以及一個 harness（Cloud Code、Cursor 或類似工具），將程式碼路徑與生產環境證據結合，產出修復方案。演講中舉了一個實例：Alex 自身系統中一個「串流被取消」的錯誤事件，被自動偵測並附上一到兩行的修復建議，不過較大型的問題通常仍需要人類介入，帶著修復方案跨過終點線。

自然的演進路徑是從在筆電上本機執行，逐步走向把同一套 skills 與 harness 搬進沙箱（sandbox）中，依排程或依生產環境錯誤觸發執行。在產品展示中（Arize 的 SaaS 平台 AX，開源對應版本為 Phoenix），Signal 針對一個示範用的金融交易代理持續運行，浮現附帶 trace 證據的問題，讓使用者可以就地建立 evaluator 或把案例加進資料集，也可以選擇在 GitHub 上開 issue。使用者可自行選擇 harness、沙箱（Arize 代管、Daytona，或 Anthropic 代管的代理）以及 skills；許多企業客戶偏好 VPC 內建的沙箱，因為他們不希望生產資料流向模型供應商。平台會追蹤由此產生的整批代理 session、可下載逐字紀錄，也能在本機續接任一 session 繼續除錯。

關於 evals，講者說明它們通常是層疊在生產環境 traces 之上的 LLM-as-judge 評估（所謂的「online evals」），一般是在觀察到特定失敗模式後才反應式地建立，以便下次能自動被攔截；它們也能大規模跨整個 trace 資料集運行，成為一層持續運作的品質檢查，供 Signal 與原始 trace 資料一併參考使用。

在問答環節，有人問為何不直接讓通用型編碼代理連接生產資料就好，講者回答：單純的直接連接效果不佳——真正的工程功夫在於設計 skills：找出正確的資料切片、把它具體化成 harness 能妥善處理的檔案格式，並賦予代理可組合的操作（例如依客戶／facet 分組），而不是給予對原始資料的直接存取。做得好的話，團隊便能記錄與追蹤比人類所能檢視多出好幾個數量級的資料，因為這些資料量如今是由代理而非人類消化，進一步朝向能夠持續自我除錯、自我改善的系統邁進。
