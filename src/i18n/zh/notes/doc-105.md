---
title: 引用不可少:為 LLM 建構的知識圖譜設計來源追溯機制
speaker: Daniel Chalef, Zep AI
---
LLM 非常擅長把多個來源的資料整合在一起，但整合過程是非確定性的——它會解讀並綜合輸入內容，產生摘要、抽取出的事實或結構化紀錄，而這個輸出結果未必會逐字出現在任何一份原始資料中。這種綜合過程摧毀了追溯的線索：法規遵循經常要求「來源可考」（provenance），但這對除錯、判斷該信任哪些來源、以及決定該刪除什麼資料同樣重要。Zep 是一套企業級 agent 記憶系統，建構於開源的時間性圖譜框架 Graffiti 之上，這兩者的設計都源自客戶一再提出的兩個問題：這個事實從哪裡來？它有多可信？

講者用一個醫療情境說明失敗模式：agent 檢索出「病患對青黴素過敏」這個事實，它是從電子病歷（EHR）、一份 PDF 檢驗報告、以及病患自己在問診聊天機器人輸入的內容綜合而來。如果醫師無法得知這個來源其實只是病患自述，而非臨床紀錄，這個事實就可能被過度信任，造成危險。天真的解法——在每個事實上存一個來源 ID——在確定性的資料倉儲中可行，但在 LLM 驅動的 context pipeline 中會失效：單一事實可能綜合自多個來源，實體會被合併（J. Smith 與 John Smith 合併成同一個身分，繼承來自多處的事實），而新資料又不斷讓舊事實失效。附加式日誌（append-only log）在這種變動頻率下難以管理，因此來源鏈結必須是一組能隨合併與失效持續演化的集合，而非靜態指標。

Graffiti 的做法是直接把來源追溯關係建模成知識圖譜：來源資料成為「episode」節點，抽取出的實體與它們之間的邊構成事實三元組，而追溯一個事實的來源，其實就是一次圖遍歷。真正困難的地方在於：當圖持續變動時，如何維持這條追溯路徑的正確性——兩個實體合併時，合併後的實體必須保留雙方原有的來源鏈結，否則來源資訊會悄悄遺失；當新資料與既有事實矛盾時，Graffiti 會將該邊標記為失效，並記錄是哪些 episode 導致了這次變動，而不是直接刪除歷史紀錄。

中繼資料（metadata）可以投射到整個圖譜上，以支援大規模的可信度檢核：在資料攝取時為 episode 加上標籤（例如「EHR 已驗證」），該標籤會傳遞給所有由此衍生的實體與事實，讓 agent 在遍歷圖譜時可以只篩選出「已驗證臨床來源」的事實。當一個事實有多個父 episode、且驗證狀態不一時，圖譜會揭露哪些父節點已驗證、哪些未驗證，但「怎樣才算足夠可信」的政策則交由應用端決定：例如過敏事實可能因攸關性命而要求所有來源都必須驗證，而另一個事實則可能容忍部分驗證——Graffiti 負責呈現資訊，套用業務規則則是 agent 的責任。

同樣的來源鏈結也解決了資料保存政策或「被遺忘權」請求下的刪除問題。如果某個事實源自三個來源，而只需刪除其中一個，只要還有另一個支持該事實的 episode 存在，該事實就會保留；如果該事實完全源自被刪除的來源，就會一併刪除。這條規則之所以簡單，正是因為父子鏈結早已存在：只有在沒有任何支持 episode 存留時，才刪除該事實。

在問答環節，Chalef 提到並非所有來源追溯資訊都存在圖譜裡——Zep 使用另一套獨立的追蹤結構（而非全部編碼進 Graffiti）來處理邊權重與關聯性的變化（例如橫跨數十條邊時）。攝取資料時的事實抽取採用單次 LLM 呼叫，一次性抽出實體、關係與候選事實三元組，成本因此較低；接著會進行去重與消歧（deconfliction）流程，合併實體並讓被取代的舊事實失效（他舉例：「Daniel 喜歡 Adidas 的鞋子」後來因「Daniel 退貨並表達不滿」而失效）。在可能的情況下，這個去重／消歧步驟會刻意避免使用 LLM，改採傳統的 NLP 與資訊檢索技術——例如 SimHash、熵值等——以求更快、更便宜、也更具確定性。當被問及當前流行的以檔案／markdown 為基礎的 agent 記憶方案時，Chalef 認為 markdown 在來源追溯上有結構性的缺陷：一旦檔案被修改，很難追溯某一行為何改變，而這個問題在多 agent、多使用者、多來源的企業情境下會被放大，儘管在單一使用者的桌面級應用場景中，檔案式記憶其實表現得還不錯。

總結而言：衍生 context 的過程本質上是有損且生成性的，因此來源追溯必須內建於資料結構本身——也就是圖譜——而不是事後補記的日誌。Graffiti 會逐字保留原始來源資料，並將所有衍生出的產物都鏈結回其來源，這帶來了內建的合規性、依據來源判斷事實可信度的能力、更容易追查事實由來的除錯能力，以及刪除決策的可靠依據。Chalef 也提到，這類圖譜建構與來源追蹤的計算成本相當高，Zep 團隊投入了大量工程心力來降低其成本與延遲。
