---
title: Lessons from Spec-driven Development
speaker: Simon Martinelli
video: https://youtu.be/odbNXv9xXjc
---
The talk opens with an origin story: building a volunteer-management system for a Swiss sports club with Windsurf in late 2024, which worked until a second organization asked for the same system with different requirements — and the speaker realized he had no clear record of what had actually been built or how to adapt it. That gap led him to spec-driven development, which he approaches differently from most tool vendors because his daily work is enterprise business applications (insurance, wholesale, retail, government) rather than greenfield products.

He distinguishes his process-centric approach from tool-centric spec-driven approaches like Amazon Kiro, GitHub Spec Kit, and BMad, which all funnel a product-requirements document into a plan and then into tasks for the agent to implement. His own "AI Unified Process" skips the plan/task phase entirely: system use cases (a specification format dating to 1987, refined through UML/RUP) plus an entity/domain model are fed directly to the agent to generate code and tests. Use cases — with actors, preconditions, postconditions, and main/alternative scenarios — are treated as strictly more expressive than user stories (a user story is essentially one flow within a use case) and, because the format is decades old, models already know how to read and write them well.

On greenfield projects, requirements engineers and business analysts produce the use cases and entity model, these are reviewed against a definition of done, and only then does an agent — equipped with stack-specific skills, MCP servers, and guardrails — generate code and tests directly, in whichever order (test-first for APIs, UI-first when a Figma design exists) fits the artifact. For his real workload, which is mostly modernization rather than new builds, the process runs in reverse: use cases and entity models are reverse-engineered from existing code, tests, and scattered documentation, reviewed by business stakeholders, and then used to regenerate the system in a new technology. Crucially, this is not lift-and-shift (which he notes has failed before, e.g. COBOL-to-C efforts): because the specification is now explicit, teams can also correct or extend behavior deliberately rather than simply porting bugs forward.

A live demo reverse-engineered the Spring PetClinic sample app into a use-case diagram, an entity model, and detailed use-case documents, then regenerated a feature end-to-end via a single "implement" command against pre-built skills — no ad hoc prompting. Reliability came from several guardrails: never let the agent scaffold the project itself (use the framework's own CLI/initializer to avoid stale dependencies); keep system-prompt files like CLAUDE.md or AGENTS.md small, since a University of Zurich study found larger system prompts correlate with more hallucination; push most guidance into versioned, iterated skills and MCP-backed documentation/vector search instead; and calibrate how much human review a change needs based on the business risk of the affected module.

Architecture choices strongly affect how well this works. Over-fragmented microservices (one client runs ~500 services and ~500 micro-frontends) spread context across too many repos for an agent to hold at once, while swinging to a single giant monolith just recreates the same problem inside one codebase. His preferred middle ground is the self-contained-systems style (contemporaneous with early microservices): vertical slices that each own their UI, business logic, and database in one place, ideally on a single technology stack per slice so skills don't have to be duplicated across frontend and backend ecosystems.

The process also reshapes teams: self-contained systems are staffed with one to two developers (two preferred, for knowledge sharing) instead of five to seven, sprints give way to continuous flow tracked as a use-case Kanban, and code review happens as ongoing pair review rather than pull requests, since trunk-based development with fast, near-deterministic generation makes long review queues unnecessary.

He closes by arguing that specs alone don't work — you need the surrounding harness of skills, guardrails, and architecture — but that specs are durable: because behavior now lives in use cases and an entity model rather than in code, the same specification could regenerate the application in a different technology, or even without a UI at all, letting business people alter system behavior without a developer in the loop. The practical effect today is that effort shifts left: requirements and specification work now consumes most of the calendar time (illustrated by a government case management project where two full-time requirements engineers support one developer doing the actual generation), while implementation compresses dramatically — provided the team deeply understands its own architecture and domain.
