title: Local AI 201: Inference Engines and the Hardware Stack
speaker: Ahmed Osman & Mike, Osmantic (with Alex, Exo)

This livestream is a hands-on follow-up to an introductory local-AI session, aimed at demystifying the sprawling ecosystem of inference engines, quantization libraries, and hardware choices. The core framing is that an inference engine is never just "hardware plus model" — it is a culmination of three factors: the hardware, the model, and the serving engine, and none of these should be picked before you know the actual application. Serving a single chat user is a completely different problem from serving an agentic workflow to twenty concurrent users, so the recommended approach is to start from the use case and work backward into engine, model, and hardware — never the reverse.

Every inference request has two phases, prefill and decode: prefill is how fast tokens and documents get ingested, decode is how fast tokens get generated (this is what "tokens per second" usually refers to). An engine's real job is to act as a traffic cop, memory manager, kernel dispatcher, and API layer so multiple requests can be handled without crashing or stalling. The two hard bottlenecks are the raw compute of the hardware and, more importantly, memory bandwidth — the speaker argues bandwidth matters more than memory capacity, since it determines decode speed and real throughput. Concrete numbers were given: DGX Spark and Strix Halo both sit around 256–273 GB/s, an M5 MacBook Pro around 600 GB/s, and an RTX Pro 6000 (Blackwell) around 1,800 GB/s. Scheduler quality and memory management matter just as much, since they determine what happens when many requests land at once.

On engine families, llama.cpp is positioned as the friendliest, most portable option — it runs on almost anything, including a Raspberry Pi, but isn't necessarily optimal for any single platform. vLLM and SGLang, by contrast, are built for concurrent, multi-user, multi-GPU serving via techniques like continuous batching. A one-page decision guide and a list of nine questions to ask before picking a stack were offered as a practical starting point, again emphasizing that the answer changes drastically depending on whether you're building a single-user chatbot or a multi-user agentic system.

The case for running locally at all rests on three points: cost control (ROI on hardware has been observed in as little as four to six months for heavy users), privacy and security (full control over a self-hosted stack versus trusting a third-party API), and stability (a locally tuned stack won't silently change the way an upstream API might, and can keep running unmodified indefinitely).

A live "hardware arena" demo compared an RTX Pro 6000, DGX Spark, Strix Halo, and M5 MacBook Pro all running the same Qwen3.6 27B Q4 model. In a single-prompt race, the ranking matched what memory bandwidth alone would predict. Under a 50x burst of the same prompt, the RTX Pro 6000 running vLLM pulled dramatically ahead because continuous batching lets it solve the prompt once and generate 50 outputs efficiently rather than reprocessing it 50 times — combined with far higher bandwidth, this produced an outsized gap. More strikingly, the M5 MacBook Pro, despite having roughly double the bandwidth of the DGX Spark and Strix Halo, performed no better than them under load, because the llama.cpp kernel it ran wasn't well optimized for its GPU — a clear demonstration that a poorly chosen kernel can erase a hardware advantage entirely.

A blind "race the cloud" test pitted the local Qwen3.6 27B model against a frontier cloud model (implied to be a GPT-series model) on the same prompt. Viewers correctly guessed the local model was on the left, mainly because of its dramatically faster time-to-first-token versus the cloud model's prefill/network latency — illustrating why latency-sensitive applications like voice agents benefit heavily from running locally.

The speakers then pitched ODS, their free open-source deployment stack, which turns what used to take months of manual integration (model downloads, engine selection, connecting front ends like Open WebUI or Hermes, coding agents, GPU/thermal monitoring) into a single install command that auto-configures a full local-AI server, leaving only the last, customizable 5% to the user.

The second half of the session shifted to Alex from Exo, who recounted Exo's origin roughly two years ago as a response to GPU scarcity and fears around GPU export controls and possible restrictions on open-weight models — the goal being to make frontier open models runnable on personal hardware via clustering, even when early results (e.g., two tokens/sec across two MacBooks) were more proof-of-concept than practical. As models have shrunk while staying capable (citing Qwen's ~35B-parameter models as an example), the interesting question has shifted from "can it run locally" to "how well does it run," which existing benchmark sites don't answer well: Artificial Analysis is built for cloud/API models where marginal token cost matters, and Spark Arena measures raw tokens/sec on local hardware without weighing task quality. Exo's answer is a new site, local.ai (in early access), which benchmarks local hardware on multi-step agentic tasks — not single-shot prompts — plotting an intelligence-vs-completion-time Pareto frontier per device (e.g., on a DGX Spark, Gemma is fastest but only 18% accurate, Qwen sits at 74% accuracy in about 4 minutes, and Step is most accurate but takes over 14 minutes). Each data point is backed by roughly 700 evaluation runs across representative agentic tasks, tested across around 100 Mac configurations and a range of Nvidia hardware, with full reproducible configs provided for each result.
