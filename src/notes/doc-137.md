---
title: Logs Are All You Need: Rethinking Observability with AI Agents
speaker: Founder, Sazabi
video: https://youtu.be/RSs0PDsULJM
---
Sazabi is an AI-native observability platform built on the premise that the slowest, most painful part of the modern software lifecycle — finding and fixing production issues — hasn't been disrupted the way coding itself has. The founder, who ran the observability team at Brex and has a love-hate relationship with tools like Datadog, frames Sazabi's approach as "AI for observability, not observability for AI," and lays out a three-part manifesto that departs sharply from how observability has traditionally been done.

The first tenet is that users should never look directly at raw telemetry — no dashboards, flame graphs, or service maps. Instead, the best UX for observability is chat: an agent with access to your logs, codebase, and other context answers questions directly (is it up, why is this customer affected, which commit broke this) the same way developers increasingly don't read their own code anymore. The second, more controversial tenet rejects the classical "three pillars" of metrics, logs, and traces in favor of logs alone. Metrics and traces are the hardest parts of instrumentation — Prometheus setup, span propagation, counters versus gauges — so Sazabi eliminates them entirely, asking only for console-log-style output, and reconstructs metrics and trace-like structure on the backend. The third tenet declares static monitors and thresholds dead: rather than using AI merely to triage or enrich existing alerts, Sazabi uses AI to generate the alerts themselves, non-deterministically, based on what its agent judges meaningful from logs, code, and context — while explicitly refusing to write or merge code itself, staying strictly read-only and instead handing off fixes to tools like Cursor or Claude Code, or filing tickets in systems like Linear per user-configured, memory-retained preferences.

On tool exposure, the discussion contrasts MCP with CLI/sandbox-based tool use and with Skills. MCP's context bloat comes from loading many tool definitions up front, a problem projects have addressed via tool search and progressive disclosure. CLI-driven agents inside a sandbox avoid this because standard Unix utilities are effectively baked into model weights — the agent already "knows" cat or grep might exist and just tries them. Skills sidestep bloat similarly: the agent only reads short markdown headers as a table of contents before loading full detail on demand, though the speakers note that overzealous skill creation risks recreating the same bloat problem MCP has.

Architecturally, the Sazabi agent runs on Vercel AI SDK workflows with a Daytona sandbox and a bash tool as its primary interface, plus a dedicated read-only SQL-like tool for querying the log database through a proxy with row-level security. Source code is made available by cloning the target repo into the sandbox, letting the agent correlate a log error with a specific commit, file, and line. Memory is entirely file-system- and git-based, similar to OpenClaw's markdown-file approach: each "project" (e.g., staging vs. production) gets its own git repository, and each conversation thread gets its own branch that is pulled at sandbox start and pushed back at the end of every command, giving persistent, shareable state across sandboxes without a traditional database. Multiple threads or sub-agents can write to shared memory concurrently, with git merge conflicts resolved by a background workflow — mirroring transactional-database guarantees but expressed as file operations, which the speaker argues agents handle more naturally than a Postgres interface. Sub-agents spawned in parallel by a main orchestrating agent each get their own sandbox but share this git-backed memory, so later sub-agents can benefit from earlier ones' findings (subject to timing/sequencing). This connects to a broader idea borrowed from evolutionary prompt-optimization approaches like GEPA: spinning up many parallel agent runs on the same task and selecting or merging the best outputs — a "map" that current tooling (including background-agent features in Codex) still lacks a good "reduce" step for.

Evaluation is treated as necessary but secondary to good context engineering, sandboxing, and sub-agent design, which alone deliver most of the quality gains; evals are what push the agent to be best-in-class by turning proprietary log data into a feedback signal. Evals are described as materially harder for CLI/bash-based tool use than for structured tool calling, since there is no single discrete action to check — a bash "execute command" tool could trigger an alert via curl, a script, or many different payloads, forcing either fuzzy LLM-based matching on command strings or checking side effects at dependent services (e.g., was the API endpoint actually hit). But as the sandbox lets users install arbitrary tools and the product's ambitions grow (e.g., autoscaling a Kubernetes cluster on AWS), the eval environment has to mirror an ever-larger slice of the real world, creating growing tension between making the product more capable and keeping it testable — addressed pragmatically by preferring local substitutes (local Postgres, LocalStack) over spinning up real external dependencies, and by building eval tooling in-house inside a TypeScript monorepo (via Turborepo) rather than buying a dedicated eval platform.

Security and compliance close the discussion: Sazabi is strictly read-only and has no public internet access by default, only reaching whitelisted domains/IPs, specifically to prevent prompt-injection-driven exfiltration of code or logs. The team also evaluates for the agent leaking its own implementation details as a competitive-protection measure, alongside standard enterprise certifications (SOC 2 Type II, ISO 27001, GDPR, HIPAA) drawn from the founders' prior experience building banking infrastructure.
