---
title: Context Engineering for Coding Agents
speaker: Fausto, JADS Applied AI Lab
video: https://youtu.be/jXtnhyro-QE
---
The starting premise is blunt: models change weekly and are opaque even to the labs that build them, so the one lever an engineer can actually pull is what gets injected into the context window. As a practical rule of thumb, never let a Claude Code session run past roughly 25% of its context budget, regardless of whether the window is 200K or a million tokens — beyond that point responses get slower, more expensive, and more error-prone, and there are easy structural fixes instead.

The talk frames context along a rough taxonomy of deterministic, probabilistic, and human-originated information. CLAUDE.md files (user, project, subfolder) are deterministically loaded with every default-agent session, but bloat fast, so path- or extension-scoped "rules" files are the better home for coding conventions. Hooks attach to lifecycle events — for example rewriting user input or post-processing a session on stop — and are useful for correcting model drift across version upgrades. Claude's built-in auto-memory is a markdown store but is still weak at knowing what to save and when to retrieve it. Scheduled loops (cron-like reruns) exist for teams with token budget to spare.

On the probabilistic side, sub-agents don't inherit CLAUDE.md, memory, or the default persona, so routing non-coding work (invoices, emails, research) to dedicated sub-agents keeps the main coding agent focused. Skills are effectively slash-commands backed by a markdown instruction file, optionally wrapping scripts or even other models — a Gemini sub-agent handling native video, for instance, called from within Claude. A skill for making skills matters more than any marketplace download (community skill packs are install-at-your-own-risk): once a chat has worked through a problem, "make it a skill" turns the findings into a reusable asset instead of scattering them across databases and stray markdown. And as the pile grows — hundreds of skills, rules, sub-agents, slightly-too-fat CLAUDE.mds — deferred tool loading (a single flag) keeps descriptions out of the window until needed, with the caveat that over-compacted descriptions leave the model too little information to pick the right skill; the recommendation is to stay lean at user scope and load full skill and MCP descriptions per project.

The human layer gets its own exhortation: read the documentation. Anthropic's docs (and the docs agent on its site) are where ideas about what's possible come from, and model upgrades keep shifting behavior — Opus 4.7, for instance, is highly opinionated, does exactly what you say (not always a good thing), and no longer prints its reasoning — so understanding the concepts matters more than memorizing details.

The talk's centerpiece is a brain analogy for memory. Working memory holds roughly seven items; what we perceive is filtered by priors ("you can only see things when you know things"); memories consolidate slowly through the hippocampus and are altered every time they're retrieved. The engineering translation — crediting Andrej Karpathy's write-up of the same idea — is a plain-markdown wiki as agent memory: no RAG pipeline, raw files stored untouched, processed whole by an LLM into concepts, entities, procedures, and code snippets, tied together by an index (browsable in Obsidian) and a hot.md that updates as information flows through. On top sit simple policies: an Ebbinghaus-style decay rule lowers a concept's score after 14–30 days unused while repeated related additions raise it, and research sub-agents instructed to download everything inject maybe the relevant 5% into the current window while banking the other 95% for later. Observer sessions — separate tmux terminals with their own CLAUDE.md, the full index, and standing instructions to know the wiki — watch the main chat's JSONL transcript and either push a wiki fetch into the main agent's context when they spot a gap, or write new findings back; Fausto offloads this token-hungry background processing to an otherwise-idle Codex subscription.

Why bother? A demo pits two identical Opus 4.7 setups — same CLAUDE.md, skills, sub-agents — against a deliberately hard task (a cellular-automata visualization) with a countdown timer injected into the session every 30 seconds. The only difference: one has a wiki pre-filled with an hour of relevant research. Under a five-minute deadline the wiki run fetches its concepts and builds; the default run must fall back on parametric memory or rushed research — and time, the talk argues, is the metric that matters.

The closing argument is about task selection: if you can't tell whether a model's output is good or bad, don't give the task to an LLM — which rules out essay-writing and (for economic as much as technical reasons) AI customer service, but makes verifiable, hard-for-humans work like extracting structured information from technical drawings the sweet spot. That framing sets up the evening's workshop challenge: extract enough JSON from a 2D engineering drawing to reconstruct the 3D model, with 55 minutes to build a memory system and five minutes on the real drawing — chosen precisely so research agents can't brute-force it inside the time limit.
