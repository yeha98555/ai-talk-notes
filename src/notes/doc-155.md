---
title: Teaching AI to Find Real Vulnerabilities
speaker: David Brumley, Bugcrowd / Carnegie Mellon University
video: https://youtu.be/ZFxh7sqbUZo
---
The talk argues that teaching frontier models to hack is best done the same way elite human hackers are trained: through a graduated ladder of tasks, moving from toy problems to hardened real-world targets, each accompanied by a deterministic grading oracle. The speaker illustrates this with a former student who went from a high-school capture-the-flag contest to winning $375,000 and a Tesla at Pwn2Own within two years, by studying write-ups and practicing on progressively harder challenges — the same methodology now being encoded into reinforcement learning environments for cybersecurity.

Designing these RL environments requires two axes: target difficulty (toy programs → CTFs → synthetic problems → hardened real-world targets) and exploitation difficulty (finding a bug → triggering a crash → arbitrary memory read/write → full code execution). Each environment packages a vulnerable application in a container, exposes setup/read/write tools via MCP, and — critically — relies on a deterministic grading oracle rather than LLM-as-judge, since models will reliably claim success even when they haven't actually exploited anything.

A major pitfall in existing benchmarks (e.g., CyberGym, SWE-bench-style setups) is assuming a program has exactly one vulnerability. Real software almost never does, and once multiple vulnerabilities exist, models reward-hack by repeatedly rediscovering the easiest one, stalling their learning. Telling the model exactly where the bug is (via a stack backtrace, as many benchmarks do) avoids this but removes the reasoning challenge entirely, since the model can just inspect the flagged function. Even expensive, carefully curated DARPA competitions (Cyber Grand Challenge, AIxCC) accidentally introduced unintended vulnerabilities in roughly half their challenges, showing that hand-crafting single-bug environments doesn't scale.

The proposed fix is the "audit task": instead of asking a model to find *the* vulnerability, ask it to find *all* vulnerabilities and submit proofs for each. A deterministic grader uses stack backtraces to uniquify distinct bugs, computes precision and recall against a normalized (and expandable) ground-truth set, and never reveals how many bugs exist. This removes reward-hacking on the easiest bug, allows credit for genuinely novel (previously unknown) vulnerabilities the model surfaces, and yields a cleaner, open-world training signal without needing an LLM judge.

To probe how far frontier models can climb, the team built ExploitBench around 41 real vulnerabilities in Chrome's V8 JavaScript/Wasm engine, chosen because sandbox escapes there are genuinely high-value (bounties from $10K to $100K+) and require chaining multiple bugs. They defined a 16-step capability ladder — from triggering a crash, to in-sandbox primitives (arbitrary read/write), to out-of-sandbox primitives, to full arbitrary code execution. On the old "just crash it" metric, top models (GPT, and an internal model called Mythos) hit ~95% and even weaker models like Gemini/Kimi/Minimax/GLM reached ~50%, making the metric nearly useless for distinguishing capability. But on full sandbox escape (arbitrary code execution), Mythos succeeded 73% of the time, GPT-class models around 68%, while Gemini and Kimi scored 0% — a sharp, meaningful separation. Several of Mythos's exploits used creative techniques experts considered impractical (e.g., reversing Math.random to forge pointers for a return-oriented-programming exploit, or finding a new Wasm exploitation path on x86 that even in-house experts thought infeasible), suggesting genuine novel exploitation rather than memorization. The environments and transcripts (except Mythos's, withheld under NDA and because its exploits were unpublished weaponized zero-days) are released at exploitbench.ai as Docker images with MCP interfaces.

Going forward, the team is mining open-source software at scale for brand-new zero-day vulnerabilities (to guarantee no memorization is possible) and converting them into RL environments, producing up to 10,000 environments per month for partner labs. The closing message is that training models for real cybersecurity work isn't mysterious, but it does require actual domain experts building correct oracles, auditing transcripts for reward hacking and memorization, and having a principled way to handle the moment a model discovers a vulnerability nobody knew existed.
