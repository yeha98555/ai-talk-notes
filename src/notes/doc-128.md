---
title: Why We Built Our Own Feature Store (and How It Scales ML at Rokt)
speaker: Aanashani, Rokt
video: https://youtu.be/qOPhghaZf-w
---
Rokt personalizes the "transaction moment" in e-commerce — the selection, cart, payment, and confirmation pages — by scoring thousands of offer combinations in real time and returning the best ranked options in under 250 milliseconds, powering billions of transactions a year. The company's ML stack evolved from simple rules-based batch logic, to logistic regression with real-time scoring, to gradient-boosted trees, to deep learning, and at each step the infrastructure lagged behind, exposing new problems: fragmented feature logic, training-serving skew, and mounting pressure from more features, more embeddings, and larger input volumes.

Without a feature store, life was messy. The same feature transformation logic was duplicated — written in SQL for training and in Go for serving — creating inconsistencies and hard-to-trace bugs. Training-serving skew was the worst offender: a model would look great offline and then fail online because its features weren't computed the same way in both places. There was no point-in-time correctness, so models could leak future data and appear accurate while failing to generalize, and no clear ownership of features scattered across notebooks, training code, and services. These gaps were expensive: one lingering bug fix uncovered a potential $5–7M revenue uptick once fixed, and a separate training bug cost $170K from a single mistake.

The fix required five things: a shared definition for every feature, point-in-time correctness baked into the system rather than left to individual discipline, consistency between training and serving, self-serve onboarding so data scientists and ML engineers could iterate independently, and clear ownership and lineage for every feature. This is exactly what a feature store promises — a single source of truth defined once, versioned, point-in-time correct, and reusable across training and real-time inference.

Rokt evaluated buying an off-the-shelf feature store around 2020–2021 but hit several walls specific to its domain. Because Rokt has no stable user ID (users don't log in the way they do on Facebook or Google), its identity system stitches together multiple session keys, and most feature stores only supported single-key lookups. Rokt also needed on-demand transformations completing in under 60 milliseconds, support for arrays and timestamps, and tight integration with its existing stack — requirements that off-the-shelf tools of the time didn't meet without major compromises. So the team built its own, prioritizing speed, deep integration, and control over its own roadmap.

The resulting system spans three core workflows. For experimentation, a domain-specific language defines features that go into a feature registry under a local namespace, so data scientists can test new features without touching production, with an SDK computing values on demand. For productionization, promoting a feature to production triggers a materializer that runs Spark-on-Kubernetes jobs (migrated from EMR for scalability) to push feature data from the data lake or Kafka into an online store — Rokt moved this store from DynamoDB to its own Cassandra cluster to control costs as feature volume grew. For real-time serving, an online API uses a prefetch DAG to compute dependent features without redundant work, a Go SDK to decide whether to hit Cassandra or use request context, and a UDF executor — migrated from Python to Go for concurrency — to run any final transformations, all within a 60-millisecond P99 latency budget.

The payoff touches the whole ML lifecycle: reusable features instead of per-model SQL and Go duplication, unified logic that eliminates training-serving drift, self-serve AB testing without depending on platform engineers, reproducibility through point-in-time snapshots and versioning, and a central registry with lineage and ownership instead of scattered definitions.

After three years building and evolving the system, the closing lesson is that a feature store is a genuine gamechanger for how fast an organization can innovate on ML, but the build-versus-buy decision hinges on fit: off-the-shelf tools now cover roughly 80% of use cases and are evolving quickly, so most teams should buy — but niche requirements, like Rokt's lack of a stable user ID, can justify building. Either way, a feature store should be treated as long-term core infrastructure, not a side project, because it becomes the backbone that makes ML consistent and scalable from experimentation through serving.
