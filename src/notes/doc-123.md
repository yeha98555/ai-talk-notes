---
title: The Unreasonable Effectiveness of Separating the Task from the Model
speaker: Maxime Rivest & Isaac Miller, DSPy
video: https://youtu.be/GgLQ02aO-hs
---
The talk argues that AI programs should be built the way software has always handled repeated work: turn the task into a function. A function has a name, defined inputs and outputs, and hidden implementation logic — which makes it reusable, composable, testable, optimizable, and shareable as a black box. DSPy, the open-source Python framework the speakers work on, tries to bring exactly these properties to AI workflows by drawing a hard boundary between what a task is and how a model currently solves it.

Examples span from small personal automations — extracting tax values from farm invoices, correcting or rewriting text pulled from the clipboard — to ambitious ones, like turning an entire inbox plus a new email into a drafted reply, or turning a spec and a repository into a pull request via recursive language models (RLMs). In every case, fixing the input/output contract lets everything behind it change freely: a simple prompt can become an agent, tools can be added, looping and orchestration can evolve, and none of it touches the calling code, because the signature never moves.

A bare input/output signature isn't enough to actually specify a task, though. The speakers frame full task specification as three complementary languages. First, natural-language instructions describe what should happen — efficient the way telling a friend the rules of a board game is efficient, but insufficient for anything that has to be learned by trial, the way AlphaZero was. Second, code encodes what must happen: hard constraints and control flow, such as rerunning an extraction with more reasoning if the first pass fails, or halting for human review if a value looks wrong — behavior you want enforced even under a hypothetical AGI. Third, examples and evaluations capture what good looks like, especially for the long tail of latent judgment that can't be stated as an instruction or a rule, learned the way an apprentice learns from many cases rather than a definition.

Once a task is expressed through specs, code, and evals together, it becomes something you can automatically optimize rather than hand-tune. DSPy's own history illustrates the trend: early on, with weaker base models, optimization meant searching for good few-shot examples; as models improved, instruction optimization became viable; and the direction of travel is toward optimizing the harness itself, so more of the implementation detail is delegated away from the engineer over time.

In production, this separation pays off in two concrete ways. Decoupling the task from the model lets teams swap in cheaper models or new techniques opportunistically and re-run the same evals, which is how Shopify reportedly cut costs 550x by moving to a cheaper model while keeping its business logic and signatures stable. It also lets the DSPy ecosystem plug in new research as it appears — recursive language models for long-context tasks, GEPA as a prompt optimizer, multi-module RL — each addable as roughly a one-line change that either helps a given problem or doesn't, without disturbing the contract around it.

Two forward-looking pieces were previewed for the next version of DSPy. DSPy.Flex extends the optimization target from few-shot examples and prompts to full custom code, letting a harness for a given function be learned over time as long as it satisfies the defined contract. Qualitative learning targets the difficulty of building evals in the first place: defining "good" for real-world tasks is hard, collapsing behavior into a binary good/bad label throws away the specifics needed to actually improve, and any fixed eval set is only a proxy for reality. The proposed direction is to let models interpret textual feedback already present in production — traces, user actions, product analytics — and convert it automatically into an evolving eval signal the system can keep climbing.

The closing point addresses the "won't AGI just solve this?" objection: intelligence isn't the same as knowing your business. Even a maximally capable model has no built-in knowledge of a specific inbox, codebase, or set of relationships — that context has to be learned over time, which is precisely the last-mile problem DSPy is built around. The recommendation for evaluating any new technique, GEPA or RLMs or otherwise, is to hold it accountable data-ically against your own defined problem rather than adopting it on reputation, and building on a shared open framework like DSPy lets that evaluation and its resulting techniques be pooled across the whole community rather than solved alone.
