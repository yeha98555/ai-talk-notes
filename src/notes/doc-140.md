---
title: From Agent Traces to Agent Simulations
speaker: Rustem Feyzkhanov, Snorkel AI
video: https://youtu.be/Ib5t2RLtxvM
---
The talk argues that every company shipping agents needs its own benchmark — not a public leaderboard number — and that the benchmark must mimic real production tools, APIs, policies, and workflows, then be continuously repopulated from live traces rather than frozen once and forgotten.

Production traces (input prompt, actions taken, output) are useful for spotting failures after the fact, but they make poor grounds for comparison: rerunning an agent against a live system means different database states, tool versions, and environments each time, so you never compare configurations apples-to-apples. Offline simulation solves this by turning traces into repeatable tasks that can be replayed under different agent configurations, scored not just on pass rate but on cost, latency, and retries, and run in parallel.

Public benchmarks like SWE-bench, Terminal-Bench, or OSWorld are useful for orienting on the frontier of model capability, but they target generic domains and tooling. A private benchmark reflects your company's actual use cases, policies, and tool surface — it's what lets you actually ship. Simulation benchmarks let you test the full agent stack (model choice, thinking budget, prompt, harness, skills, tools) rather than just swapping models, since production performance depends on the whole system.

A benchmark task has an anatomy borrowed from formats like Harbor: an instructions file the agent sees, an environment (Dockerfile/Compose), an Oracle solution and verifiers the agent never sees, and metadata. The Oracle matters because it proves the task is actually solvable before you ever run an agent against it. Environments should be "mini production" — real-shaped databases, mocked or sidecar API services, and simulated users (an LLM playing a human) — using snapshots rather than full production data, with multi-step structure and early termination to handle long-horizon tasks.

Verification goes beyond checking final output: it can inspect final environment state, tool calls, and the full trace using deterministic checks, LLM/agent-as-judge, or targeted subject-matter-expert review — reserving human review for cases where the automated judges disagree or a genuine edge case appears, rather than reviewing everything.

Benchmark tasks can fail in several ways: agents reward-hack an environment they recognize as simulated, verifiers are too loose (agent always passes) or too strict (agent always fails), or success is unstable across repeated runs. Because a benchmark is effectively software, it deserves its own CI: pinned dependencies, correct base images, fixture checks, Oracle runs to confirm solvability, and repeated agent runs to tag task difficulty before approval.

Once running, the mature setup is two connected loops: an expansion loop that pulls failures from observability tooling into the growing benchmark, and an experimentation loop that reruns the benchmark against new agent configs and gates releases on measurable, non-regressive improvement. This structure also discourages the common anti-pattern of dumping every fix into the prompt ('never do X'); with full-stack control you can instead fix the harness, add a skill, or enforce a structured output schema wherever the fix actually belongs. Benchmarks constructed this way serve triple duty: agent evaluation, release-gating integration tests, and even training data for fine-tuning smaller models to match larger ones on specific tasks.
