---
title: AI Agents for Performance: Ship Faster, Pay Less
speaker: Rajat Shah, Netflix
video: https://youtu.be/CgsWxRUY5Eo
---
This talk presents a practitioner's playbook for using AI agents to close the gap opened by AI-accelerated coding: engineers now ship code far faster than before, but that code isn't necessarily performant, and the manual process a human performance engineer uses to find and fix bottlenecks — trigger profiling, download a raw call-stack dump, load it into a visualizer, hunt for hot paths, search the codebase, and eventually send a fix — takes many minutes of tedious, specialized work per service, so it's rarely done except in 2 a.m. fire drills.

The core question was whether an LLM agent could replace that 20-minute manual triage. Two assumptions made this plausible: profiler output is structurally similar across languages and runtimes (call stacks, self CPU, inclusive CPU, sampled at high frequency), so an agent doesn't need language-specific tooling to read it; and coding agents have already seen enough public code to recognize common anti-patterns — O(N²) loops, loop-invariant recomputation, repeated object allocation, missed batching opportunities — purely from call-stack shape, without even looking at source. In practice, once an agent spots a suspicious pattern in profiling data, it can check out the exact production commit, locate the method, trace its full call path, and propose a fix — all four steps in under five minutes on a large codebase. In one real case this caught an O(N²) implementation responsible for 8.8% of CPU time; in another, the agent generalized a single bad pattern (a metrics counter object recreated on every hot-path iteration) and searched across repos to find the same anti-pattern reused in seven different services, worth an estimated 0.5–4.6% CPU savings if fixed everywhere.

To make this systematic rather than one-off, the key infrastructure is a long-term, fleet-wide memory of patterns and anti-patterns — not a vector database, just markdown files in a central Git repo, human- and agent-readable and -writable. Each entry records symbols, the services where the pattern was confirmed, and a confidence score that rises as more services validate it. This catalog can be bootstrapped from public sources (e.g., Jeff Dean's C++ optimization notes, PyTorch's torchfix anti-pattern repo) or an org's own performance playbooks, and it compounds: once one service's profiling run identifies a pattern, every future agent profiling any other service can reuse that finding instantly instead of rediscovering it.

Because an agent modifying already-working production code is inherently risky, human approval stays in the loop, and noise is filtered before a review ever reaches a person: the agent must first pass existing unit/integration tests, then run a canary comparing old versus new code on live traffic to check CPU, latency, and error-rate deltas. Only fixes that clear both functional-correctness and canary ground-truth checks get surfaced as code reviews — the mental model being that the profiler provides estimates, the canary provides ground truth, and the engineer still makes the final call.

The longer-term ambition is to shift this leftward along the software development lifecycle: from the reactive mode (finding and fixing bad patterns already in production), to review time — where a review agent annotates anti-patterns inline against the catalog — and ideally to write time, where the coding agent consults the catalog before generating code so inefficient code never gets written in the first place. Write-time integration adds latency and token cost, so the catalog has to be well indexed and support hierarchical, low-context lookups rather than being dumped wholesale into the prompt.

The closing advice is to build the foundations before layering on agent autonomy — solid test coverage, reliable canary automation, and a well-maintained pattern catalog — and to start with the reactive path rather than trying to automate everything at once. The talk frames this as a staged spectrum of autonomy: stage one is fully manual profiling with no LLM involved; stage two — the bulk of this talk — is a fixed, predefined agent workflow (trigger profiling, analyze, canary, propose fixes) that can be scheduled weekly to catch fresh regressions; stage three grants the agent open-ended planning and reasoning autonomy, but demands serious investment in evals and sandboxing to guard against risks like prompt injection. The recommendation: start at stage one, move to stage two for most of the benefit, and only consider stage three once the guardrails are in place.
