---
title: Building Code-Editing Agents: The Emperor Has No Clothes
speaker: Jeff Huntley, Sourcegraph (AMP)
video: https://youtu.be/OR3zdu9T_as
---
The talk's central provocation is that a coding agent is nothing mystical: it is roughly 300 lines of code running in a loop, repeatedly sending the conversation so far to an LLM for inference and checking whether the model wants to call a tool. Tools like Claude Code, Cursor, Windsurf, GitHub Copilot, and AMP are all built on this same primitive loop; what tooling vendors add on top are small hints (you're on macOS, use forward slashes, use PowerShell) and prompt tuning, but the model itself does essentially all the heavy lifting. The speaker builds a coding agent live, from scratch, incrementally, to demonstrate this.

A first key idea is that not all LLMs are equally agentic. Models can be mapped on a quadrant crossing safety alignment against agentic tool-calling tendency: a low-safety model like Grok suits security research, high-safety models like Anthropic's or OpenAI's suit ethics-sensitive work, "oracle" models like o3 excel at summarization and high-level reasoning but resist taking action, while models like Claude Sonnet behave like an eager squirrel constantly chasing tool calls. Comparing models purely on price and context-window size misses this — it's like judging cars only by door count while ignoring that some are built for off-roading and others for people-moving. Combining models plays to these strengths, e.g. using an agentic model to do the work and an oracle to check it.

The second key idea is ruthless context-window hygiene. The window should be dedicated to a single activity at a time — mixing unrelated concerns (add a route vs. rebrand the site) causes needle-in-haystack confusion, so starting a new chat per task is the practical fix. The window is also smaller than it appears once the system prompt and tool definitions eat into it, and every registered MCP server adds its own "billboard" describing how to call it, which further consumes the budget and can make the model measurably dumber. The advice is to avoid indiscriminately enabling MCP servers — foundation models are often already trained on standard CLIs (e.g., the GitHub CLI), so a dedicated MCP is unnecessary unless doing genuine server-to-server integration.

The live build itself walks through the minimal primitives that stack into a real coding agent: a bare chat loop with no tools; a weather-style function call to illustrate that a tool or MCP is just "a function with a billboard on top" describing how the LLM should invoke it; a list_files tool so the agent can see the repository layout; a read_file tool so it can pull specific file contents into context (demonstrated by having it solve a riddle from a text file); a bash tool for executing system commands (summarizing top CPU processes); and finally an edit tool, which combined with the others lets the agent scaffold a small Node/TypeScript FizzBuzz app, run it, validate the output, and then modify it on a follow-up instruction. Each primitive is deliberately small and composable, and observed failures in tool-calling accuracy are exactly what tooling teams tune system- and tool-level prompts against.

The closing argument is cultural rather than technical: understanding how to build an agent from first principles is becoming baseline engineering literacy, on par with knowing what a primary key is, because it turns people from consumers of AI into producers who can automate real job functions in their own domain (the speaker cites an engineer who used this knowledge to automate work previously done by twenty people). The risk of disruption comes not from AI itself but from failing to invest in this skill. Not every problem should be solved with an agent, but building one's own develops the instinct for where autonomy is safe, where a human needs to stay in the loop, and how many chained agent-to-agent hops a task can tolerate before results degrade.
