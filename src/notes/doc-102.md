---
title: Harness Engineering is not Enough: Why Software Factories Fail
speaker: Dex Horthy, HumanLayer
video: https://youtu.be/Ib5GBkD555M
---
The talk opens by naming the prevailing narrative in AI coding: models are good enough, code is free, you are the bottleneck, so just spend more tokens and stop reading the code. Against this, the speaker points to mounting evidence of cracks — companies that shouldn't be having outages are having them because of coding-agent mishaps, codebases are degrading faster than ever, and a report from Faros AI shows that since teams broadly adopted AI coding tools, pull-request review quality has dropped, comments have gotten longer and more numerous, more PRs merge with no review at all, and incidents and bugs per developer are both up. The core claim is that this is not a scale problem solvable by more harness engineering or cleverer loops — it's a model-training problem.

To make this concrete, the talk traces a brief history of the "software factory," a term coined at a 1968 NATO conference. In a 2022 software factory, engineers pull work from a tracker, build it, and pass it through PR review and testing before shipping, with user feedback and monitoring looping back into planning. Teams learned decades ago that upfront planning and architecture reviews reduce rework and shorten review cycles. The agentic software factory simply swaps an agent into the "build" step, which now takes minutes instead of days — but human review and testing remain the bottleneck. The natural next moves are agentic code review and regression testing, then routing incidents and user feedback straight back into the agent loop, culminating in the "lights-off software factory" (a term from Dan Shapiro) where code review is abandoned entirely and the only job left is deciding how much work to queue up. The speaker states plainly that this does not work, drawing on HumanLayer's own experience going fully lights-off in July 2025: after a few months, they hit problems the agent couldn't solve even with advanced prompting, requiring humans to dig back into code nobody had read in months while sites were down and users were angry.

The underlying issue is that models can't maintain and improve codebase quality over time without significant human steering — codebases become fragile, where changes in one place break other parts (Martin Fowler's "shotgun surgery" smell). This holds even for the newest models: they've improved a lot at one-off tasks and greenfield projects, but not visibly at long-term maintainability, partly because no good benchmark exists for that ability yet.

To explain why, the talk revisits why Claude Code became the first breakout coding agent despite other CLI agents (Aider, Codebuff) having the same read/write/edit/grep/bash tools: Anthropic was the first lab to train a model directly against the harness it shipped to users, letting it RL against its own tool-calling loop — an advantage a harness builder without model weights can't match. Standard coding RL (illustrated with SWE-bench-style tasks) generates many solution traces, scores them by whether tests pass without breaking others, and reinforces the successful ones. But this reward signal only checks test-passing, not program design, so nothing penalizes ugly patches like unnecessary try/catches or type-casting hacks used purely to satisfy a test — because verifying maintainability is far harder than verifying that tests pass, since the cost of bad architecture only shows up months or years later, making the reward signal nearly impossible to propagate back to the training episode.

Newer benchmarks are trying to close this gap — SWE Marathon (Abundant AI) with ~400-hour tasks like recreating all of Excel's features, Deep Suite (DataCurve) using large out-of-training-set repos, and Frontier Code (Cognition), which penalizes tests that don't fail on pre-patch code and uses a judge model to check code-quality rules. But the speaker argues judge models have a ceiling: if a model truly knew what good code looked like, it would write it in the first place, so review agents and extra tokens can raise the floor but not remove the underlying constraint on what RL can currently teach. For now, the conclusion is that humans are still stuck reading the code.

Given that, the practical advice is to re-engineer the workflow around this constraint rather than wait for a better model. This means turning code review back on and investing upfront in product review (clarifying the problem and desired behavior, using mockups), system architecture (component contracts, data models, constraints), and — an often-skipped step — program design (types, method signatures, call stacks, call graphs, an approach also used by Cloudflare's Dylan Mulroy), followed by vertical slices that define implementation order and checkpoints across the whole system. Thirty minutes of upfront planning and alignment can save hours in review, making it feasible to still read every line of code. The real problem with drowning in PRs isn't too many PRs but too many bad ones; a well-aligned PR is fast and pleasant to review, while even a PR needing 20% rework is a heavy emotional and intellectual burden on both submitter and reviewer. Model-assisted planning shortens alignment, speeds review because everyone aligned upfront, and speeds coding because AI wrote it — letting teams move genuinely faster while still owning and reading their code.

The talk closes by reframing this as an engineering-with-constraints problem rather than a reason for pessimism: models are good at some things and not others, so the job is to find leverage within those limits rather than assume the models will simply get good enough. The speaker's company, HumanLayer, is building an AI IDE and collaboration platform — described as a Figma-like collaborative workspace for Claude Code/Codex-style workflows — aimed at supporting this planning-and-review-first approach, with better verifiers for software quality positioned as future work.
