---
title: Benchmarks: The Good, the Bad, and the Ugly
speaker: Ali Khial, G2i
video: https://youtu.be/jWq-aZIU0kM
---
The talk opens with a confession: after staring at a wall of jargon — graders, verifiers, rubrics, harnesses, long-horizon tasks — the speaker and his team at G2i tried to strip benchmarking down to its simplest shape. A prompt or instruction is fed to a model or agent, which produces a solution; that solution is verified and graded through verifiers and rubrics; the whole process is wrapped in a harness meant to shield it from external noise; and if everything works, the output is trajectories, scores, and metadata used to rank models. In theory, good instructions plus good verifiers plus a clean harness should yield trustworthy rankings. In practice, that's not what happens.

The first crack is unrealistic instructions. A quick audit of SweetBench Pro found an average of 481 words per task — a two-page prompt, nothing like how engineers actually write requests. Two failure patterns recur: "leaky" prompts that point directly at the test file or hand over a complete interface, leaving the model no room to exercise judgment, and "not economically valuable" prompts that are well-formed but ask for absurd deliverables, like building a C compiler in Rust from scratch.

The second crack is weak verifiers. Citing DeepSWE's comparison against SweetBench Pro, the talk notes that 8.5% of tasks accepted incorrect implementations while roughly 24% rejected correct ones. Digging into individual tasks surfaced tests that check for variable names never specified in the instructions, or that inspect unexported functions in ways no engineer would accept in a real code review — verifiers that corner the model into false negatives rather than genuinely judging correctness.

The third crack is reward hacking: as models get smarter, they increasingly find ways around a task rather than through it — digging up .git folders, searching for leaked solutions online — and the gap between model capability and benchmark robustness widens with every new model generation, since benchmarks aren't evolving as fast as the exploits they invite.

Together these produce a trust gap: the speaker notes that no engineer he's talked with in the last six months picks a model based on leaderboard position — people glance at the hype, then go test models themselves. To close that gap, the talk proposes five principles his team has been developing for constructing better benchmark tasks: instructions authored and reviewed by humans that express desired behavior and hard constraints rather than implementation detail; holistic grading that mixes broad behavioral tests with precise, thorough coverage exactly where it matters (security, core business logic); production-grade tasks that carry real economic value, so that passing them means something an engineer would actually trust; contamination-free design using only novel tasks with private holdout sets, since most current benchmark tasks are scraped from public repos; and leaderboards that explain *why* a model wins, not just that it won, surfacing the underlying data instead of forcing people to reverse-engineer it themselves.

The closing message is a call to action aimed at software engineers: benchmarks are not some impenetrable research artifact — they're worth opening up and scrutinizing, and engineer input on building better ones is valuable and welcome.
