---
title: Why AI Agents Need a Data Harness, Not Just a Lakehouse
speaker: Will Martin, Dremio
video: https://youtu.be/xR-BiPz45-4
---
The talk opens with a framing shift: legacy analytics ran on "email pace" — a query could take minutes or hours and that was fine, because a human would just go make tea and check back later. Agentic workflows run on "conversation pace" instead — if an agent has to wait ten seconds for data, the pipeline stalls, tokens burn, and the interaction breaks down. Sub-second response isn't a nice-to-have for AI-driven data access, it's a hard requirement, and that requirement is what separates a mere data lakehouse from what the speaker calls a "data harness."

The groundwork is a fairly standard lakehouse story: warehouses are great for querying but expensive to store at scale; lakes are cheap to store but painful to query; a lakehouse combines cheap object storage with a metadata catalog and a table format (Iceberg) to get warehouse-like reliability and transactions on top of lake-like economics. Dremio's own stack is built entirely on open standards — Parquet for files, Iceberg as the only table format, Apache Polaris as the open catalog, and an Arrow-based query engine — and the talk argues this open-standards commitment (versus a closed, vendor-specific stack) is itself a prerequisite for building a harness that isn't locked in.

Three components of the execution layer are said to jointly constitute the "performance data harness": the catalog, the semantic layer, and the query engine. The catalog (Polaris) handles governance and optimization — role-based and fine-grained row/column access control, credential vending down to the storage level, and table-maintenance mechanics like compaction (fixing the "small file problem"), vacuuming stale metadata, and Iceberg clustering as a friendlier alternative to partitioning. A newer feature, variant shredding, lets semi-structured (JSON-like) data sit in a table cell while still being pulled apart for predicate pushdown, preserving the query-pruning speed that makes table formats fast in the first place.

The semantic layer addresses a problem that predates AI but is sharpened by it: business terms like "customer" or "revenue" are rarely universal even inside one company, and these definitions usually live outside the data platform — in BI tools, spreadsheets, or people's heads — where neither humans nor models can find them. An LLM trained on general data has no access to a company's specific definitions and will "guess with confidence," producing results nobody can fully trust. Consolidating metric definitions, table relationships, and column meanings into one semantic layer alongside the data gives an agent a reliable place to resolve ambiguous business language before it writes a query. The talk notes an emerging industry effort here, the Open Semantic Interchange (OSI), now an Apache Software Foundation project backed by companies like Salesforce and Snowflake, aimed at standardizing how semantic context is shared across tools, though concrete implementations still vary.

The query engine's role is federation: rather than physically centralizing data (the trap warehouses fell into), it queries data where it lives across silos, other catalogs, databases, and object storage, centralizing access and governance without centralizing storage. Performance comes from layered caching — query plan caching, cached result sets, and a columnar cloud cache that keeps frequently accessed data on compute nodes, reportedly cutting costs by up to 90% for some customers by exploiting otherwise idle local storage.

Because all of this rests on open specs — especially the Iceberg REST spec — engines and catalogs are largely interchangeable: any compliant engine can talk to any compliant catalog out of the box, letting teams assemble a lakehouse platform suited to their own performance, cost, or organizational constraints rather than being tied to one vendor. AI access into this harness is exposed three ways — a built-in UI agent for non-technical users, MCP for general integration, and a CLI for programmatic, multi-agent workflows — with the semantic layer acting as the common context and permission boundary underneath all three, so an agent always queries as the credentialed user it's acting on behalf of.

The closing summary distills the requirements shared by analytics and engineering workloads: data must be accessible (governed, but broadly reachable), understandable (via shared, agreed-upon semantic definitions rather than ad hoc interpretation), and performant (queried in place, without unnecessary movement or waiting) — and all of this should be deliverable on open standards so organizations aren't locked into a single vendor to get it.
