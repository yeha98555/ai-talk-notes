---
title: CrabRAG: Why Automated Assistants Need Graph Memory, Not More Tokens
speaker: Stephen Chin, Neo4j
video: https://youtu.be/Q0VkgCyNVUg
---
The talk opens with a mascot, Crab D, a well-meaning personal assistant who keeps forgetting everything overnight and keeps reaching for the wrong tool. The joke sets up a serious point: as agents take on more autonomous, long-running work, the bottleneck isn't intelligence but memory — what gets put into context and what gets recalled from it.

The survey of current approaches starts with the simplest: memory as plain markdown files, the pattern used by tools like OpenClaw, with daily memory files, tool files, and skill files. Markdown is human-readable and easy to compact, but an agent ends up loading everything on the chance something will be useful — average sessions were pulling in over 100k tokens per round. That works at small scale with a strong model but breaks down as scope grows, because it's repetitive and wastes context rather than targeting what's relevant.

Skills-based systems, exemplified by Hermes agent, improve on this by having the agent reflect after each task and update or add skills — but skills are still just markdown files, and the system only works if the right skill gets loaded. Pick the wrong skill, or miss a needed step in a skill chain, and the agent stalls exactly where a human wouldn't. A cited research direction — modeling skills as a graph — is offered as one way to address that chaining problem.

MCP-based memory, as in the Goose project (part of the new Agentic AI Foundation), treats memory as just another pluggable server: commands to remember, retrieve, and forget, backed by files on disk. This adds flexibility but doesn't fix the underlying problem — memory is still markdown on disk, it can grow unwieldy, and because forgetting is now literally an MCP tool call, an agent is one bad call away from wiping its own memory.

Vector databases are the next step up: embed everything, store it in something like pgvector or LanceDB, and retrieve by similarity. This scales further and pulls back genuinely related information, but similarity in vector space isn't the same as an actual relationship. The result is hallucination-prone answers, especially on multi-hop questions that require chaining several true facts together — vector search alone can't reliably do that reasoning, and superficially similar facts get retrieved as if they were the right ones.

Graphs address this directly: entities become first-class nodes, relationships become edges, and properties (including embeddings) attach to either, so vector and graph retrieval can be combined. The demo architecture uses a vector search to find seed nodes, then a graph traversal outward from those seeds, ranking neighbors by relevance to assemble a precise, multi-hop answer. The payoff is accuracy, explainability (you can inspect the graph that produced an answer), and auditability (you can see exactly which subgraph fed the context) — and Claude turns out to be quite capable of writing the Cypher and entity extraction needed to build this without the developer being a graph expert.

To test this, the speaker built a full digital twin of his home lab network as a graph, using Cognee (a startup with a Neo4j backend) alongside an equivalent vector-store setup built from the same source markdown, both cut off from live network access so answers had to come purely from memory. Asked to find WAN-exposed, end-of-life software, the vector-based agent returned a vague non-answer; the graph-based agent correctly traced from seed nodes through one-hop neighbors to identify the exact outdated, internet-exposed server. A second query about exposed 0.0.0.0 management ports produced the same pattern: the vector agent punted the work back to the user, while the graph agent followed the router node directly to the two genuinely exposed services.

The closing argument is about scale: a four-node home lab is a toy case, but enterprises with large data centers or large customer/financial datasets that don't fit into even a one-million-token context window need something better than markdown-file memory. The talk points to a forthcoming book, "GraphRAG: The Definitive Guide," covering graph memory and agent architecture across industry use cases, plus Neo4j's free GraphAcademy courses on agent memory and context graphs as ways to get started.
