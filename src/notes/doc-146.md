---
title: Harness Engineering: Building an AI Software Factory
speaker: Dru, Tessl
video: https://youtu.be/bUtAGFXPc3A
---
The talk introduces "harness engineering" (also called loop engineering, meta engineering, or software-factory building) as the emerging discipline that replaces writing and babysitting code with building and monitoring the loops that let agents write, review, and maintain code themselves. A software factory is the end state: an agent system that builds the shipped product end to end while humans shape tickets and tasks and work to raise the system's autonomy, automation, and quality.

Three metrics anchor the journey. Autonomy is how many course corrections an agent needs to reach a correct answer — measurable by human turns or PR comments. Automation is how much oversight agents still require even once they're autonomous; teams often unlock autonomy but stay bottlenecked on review because they haven't yet built trust. Quality is simply whether the shipped product stays good as more work is delegated.

The case for building a factory rests on more than speed. Velocity comes first and comes fast, but the bigger shift is quality: agents make tireless code reviewers, so review capacity is no longer capped by human fatigue, and companies further along adoption are already seeing bug counts drop as review effort scales up. Separately, most bugs today are known but permanently deprioritized on a backlog; once capacity is abundant, backlogs largely disappear and niche, previously unprioritized issues finally get fixed. A factory also removes the gatekeeping on who can contribute code — people from GTM, design, or people-ops can land production PRs — and, in the speaker's view, simply makes the remaining human work (architecture, system design, how things scale) more enjoyable, since that's most of what's left to do.

Building a factory is not a rip-and-replace event; it's incremental — identify a workflow, box it up for an agent, run it interactively until confident, then automate it, one workflow at a time. The real question isn't whether to build a factory but what percentage of one you want to be.

Harness engineering itself is organized around three loops. The inner loop drives autonomy: unit tests, linters, and manual checks that an agent hill-climbs against before opening a PR — and because agents maintain these suites themselves, teams can afford to be far pickier than they ever were with humans. The outer loop drives automation: slower, deeper checks like agentic code review or an agent clicking through a running build and taking screenshots, building confidence so a human doesn't have to inspect everything. The meta loop is the previous two loops running on autopilot: agents that scan a week of CI failures or PR comments, spot recurring mistakes, and propose new lint rules, skills, or tests — this is where most time eventually gets spent, since it converts reactive firefighting into reviewing suggestions.

Harness engineering is mostly hard for organizational reasons rather than technical ones. Best practices change constantly and keeping up isn't anyone's day job. The correct response to an agent failure is to throw away the PR, diagnose what missing check or skill would have prevented it, and retry — which feels like unplanned work and is a hard sell when a two-hour fix was sitting right there. And legibility is poor: teams don't realize they're hitting the same pain points until it surfaces slowly through conversation.

A few concrete components make this tractable. The single highest-leverage change is moving from interactive, one-shot agent sessions to an issue-tracker-and-PR workflow, where tickets and PR comments become the legible surface agents and humans both operate on; OpenAI reportedly saw a 5x productivity gain moving fully to this model. From there, teams accumulate playbooks and skills rapidly (five in a week, thousands soon after), which motivates a skills registry — an npm-like way to share, version, and propagate improvements. A large share of early effort goes into "agent-ifying" access: giving agents CLIs, sandboxed cloud environments, and read access to a "company brain" (Slack, docs, internal services) so they aren't blocked by human-only logins. Finally, improvement loops close the system: maintenance agents that scan recent logs, issues, and PR comments, propose fixes or new automations, and either self-merge in low-risk areas or route through human review for anything production-facing.

Tessl positions itself as a platform for building these factories: an agent interface that keeps up with shifting best practices, skills and review logic stored as plain files in the repo rather than locked in black boxes, a skills/plugin registry with evals and security checks, default GitHub/Linear integrations, and "verifiers" — small, cheap LLM-powered lint-style checks (reportedly ~$0.30 for a day's worth of PR reviews across 100+ verifiers, versus roughly $25 for a full agentic PR review) that shift review left into the inner loop. A change-risk analyzer scans PRs against a team's agreed quality policy to decide whether a PR can auto-merge or needs human eyes.

The closing guidance is to track a small set of numbers as a factory matures: drive down manual takeovers (human PR comments, manual ticket decomposition), drive up the share of PRs initiated automatically by maintenance agents, and improve — never just tolerate — code quality, starting with the hard problem of how to measure it at all rather than accepting speed at the cost of quality.
