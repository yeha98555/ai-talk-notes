---
title: Learned Execution Graphs for Anomaly Detection & Drift in APIs
speaker: Ritvik Pandya, JP Morgan Chase
video: https://youtu.be/u1yaOeEX4e8
---
This talk introduces the idea of a "learned execution graph" — a short-lived, per-request DAG that represents how a single request actually flows through a distributed system, and uses that representation to detect anomalies and drift far faster than traditional threshold-based alerting. Unlike persistent property graphs (Neo4j and similar), this graph exists only for the lifetime of a request: it captures the order in which services execute, the context passed at each node, and treats retries or loops as their own tracked entities.

The core workflow is tiered, modeled on airport security: a cheap tier-one check compares a request's end-to-end timing against a learned baseline, and only if something looks off does the system escalate to a deeper tier-two analysis that localizes which node deviated — a new or missing step (structural drift), a slowdown from volume growth (scale drift), or a shift in the mix of traffic, such as a growing share of international requests each needing an extra currency-conversion step (covariate drift). In a payments example, the system pinpoints that a foreign-exchange rate service, not the pipeline as a whole, is responsible for added latency, letting the team fix the actual bottleneck rather than chase a vague overall slowdown. Baselines and thresholds were trained using OpenTelemetry traces and the star-bench benchmark, injecting millions of traces and synthetic anomalies over a multi-day window before deploying live.

The talk draws a careful distinction between anomaly (a one-off spike, like unusual traffic on a normal commute) and drift (a persistent pattern shift, like a commute that has quietly gotten twenty minutes longer over a year) — the former may need a transient response, the latter requires re-baselining. Drift is further split into structural (nodes added/removed), scale (volume outgrowing service capacity, requiring scaling or async processing), and covariate (the request mix itself changing, requiring separate baselines per segment, e.g., domestic vs. international, or per endpoint type rather than one generic "POST" baseline).

The production pipeline streams OpenTelemetry data asynchronously (e.g., via Kafka) into two paths: a hot path for fast, low-latency automated decisions, and a slower, more accurate reconciliation path for deeper root-cause analysis. Once a drift type is classified, the system estimates the risk of automating a fix, then rolls it out incrementally — first to 5–10% of nodes, verified, before going to 100%.

Several practical tuning issues round out the talk: a node that merely delays sending its telemetry event can look like a structural change (a missing node) if not handled carefully, so the system uses tail-based sampling keyed to when each service request actually starts and ends, and treats new endpoints as cold starts needing their own baseline rather than inheriting a generic one. MMD and KL-divergence style detectors are used on the analysis side, with human admin confirmation feeding classification. The reported payoff is a large reduction in mean time to discovery, moving from comparing across multiple time windows to detecting issues within a single window. Closing recommendations: fine-tune labels, keep baselines segmented by specific use case (e.g., real-time wire payments vs. general POST traffic) rather than one-size-fits-all, define drift-detection windows per client, make results explainable rather than an opaque score, and keep the system aware of new deployments so it can inform rollback decisions.
