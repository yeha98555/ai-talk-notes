---
title: Loop Engineering from First Principles
speaker: Kyle Mistele, HumanLayer
video: https://youtu.be/xIt_mTQp6mY
---
The talk opens with a critique of the current hype around "Ralph" loops — piping a prompt into a coding agent in a bash loop until it converges. Jeff Huntley's original Ralph technique is a sharp tool for solo hackers building throwaway systems, but most engineers work on teams, on critical systems, with SLAs and regulatory obligations, where blind loops just produce 40,000-line PRs nobody wants to review. The goal of the talk is to show how to design loops that work for that real-world context: large, complex, team-owned codebases with real users.

The core idea borrows from control theory, the discipline behind thermostats, Kubernetes autoscalers, infrastructure-as-code reconcilers, Postgres autovacuum, and React's virtual DOM. A control loop has a sensor that measures current state, a set point describing desired state, a controller that turns the gap between them into an incremental change, and an actuator that applies it — all while the system absorbs outside disturbances and gets re-measured. Control loops are ideal whenever you have something measurable, a way to change it, and a way to get feedback on the result, and they work by making small, reversible changes rather than lurching straight to an end state and risking instability. This is presented as the opposite of a "blind Ralph loop," and the best Ralph-style loops, done well, are actually already approximating control theory.

Building an agentic control loop starts with defining the set point (the desired property of the codebase) and a sensor, which can be strictly deterministic (linters, ASTGrep, type checks), fully agentic (a model plus a skill and natural-language rules), or a hybrid pipeline of both. Because agents blur the boundaries between components, a tool can act as both sensor and controller at once (e.g., a React linting agent that both flags issues and ranks fixes), and a single agent can serve as both controller and actuator, deciding on a change and applying it in one context window. The controller matters most: without a well-tuned one, the loop risks making too large or too wrong a change, which compounds badly once looped.

The pattern is illustrated with HumanLayer's internal loop for migrating their RPC API to the Effect library. The sensor uses ASTGrep — language-agnostic, out-of-band from linter configs an agent might quietly disable — to find unmigrated procedures across a multilingual monorepo. Because a full scan produces too many violations to act on live, the team runs one deterministic baseline scan on main, commits the sorted violation list to version control, and then gates new PRs so nobody can add further unmigrated code — a "disturbance dampener" that stops the bleeding before incremental fixes begin. The controller can be as simple as deterministically picking the smallest violation (to minimize risk), or smarter: cross-referencing telemetry to prioritize procedures with the most errors or weakest instrumentation, so the migration also improves error handling and observability rather than being a rote rewrite. The actuator is an agent plus a carefully engineered, iterated skill, ideally seeded with hand-written "golden pattern" examples so the agent has an idiomatic template to replicate rather than relying on generic internet knowledge; it produces a final response used verbatim as the PR description, then the loop deterministically commits, pushes, and opens the PR.

Running this as a scheduled GitHub Actions workflow (chosen for its existing access to code, secrets, and scheduling primitives) turns it into a daily cadence of small, low-risk PRs. Two refinements make it sustainable: a version-controlled feedback markdown file that gets loaded into the actuator's context every run, updatable via a `/iterate` PR comment that triggers the workflow to pull in the diff, review comments, and description and revise both the code and the feedback file — giving humans a low-friction way to resteer the loop over time with a visible history of changes; and flow control, where each loop checks whether its own previously labeled PR is still open before running again, skipping the run if so, so at most one unreviewed PR per loop ever exists and work doesn't stack, duplicate, or conflict while nobody's watching. Once confidence is high, throughput can be increased by having the controller select and execute multiple violations per run, splitting them into separate implementation phases for cheaper, more reliable per-item context windows, or by fanning the workflow out across a team.

The closing takeaway is that this is still building loops — but loops designed with control-theory discipline: incremental, measurable, human-reviewable, self-throttling, and steerable, aimed at making hard problems in complex, high-stakes codebases tractable rather than dumping unreadable volumes of agent-generated code on a team.
